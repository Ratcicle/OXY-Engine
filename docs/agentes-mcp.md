# Agentes de IA (MCP)

A OXY Engine traz um servidor MCP, o `oxy-mcp.exe`, que deixa agentes de IA como o Claude ajudarem no desenvolvimento dos jogos. Com ele, o agente:
- cria um projeto novo, quando você pede, na pasta que você indicar;
- lê o projeto e consulta a API dos scripts e o catálogo do que os comandos criam;
- edita cenas, objetos, componentes e lógica;
- escreve, confere e anexa scripts em Luau;
- importa imagens PNG e sons WAV;
- valida o projeto;
- roda o jogo sem janela para testar;
- testa o jogo no editor, para você ver, sem tomar o seu mouse;
- captura imagens;
- salva o projeto aberto, só se você permitir;
- exporta o jogo, quando você pede, para a pasta que você indicar.

## Configurar

1. **No editor:** abra **Preferências do editor** (o botão **Interface: 100%** na barra de status) e ligue **Permitir agentes de IA**. A opção começa desligada. Com ela ligada, a barra de status mostra **Agentes ligados**, ou **Agente conectado** quando um agente está conectado. Logo abaixo, **Permitir que agentes salvem**, também desligada por padrão, deixa o agente salvar o projeto (veja [Salvar ao vivo](#salvar-ao-vivo)); ela só pode ser ligada com os agentes permitidos.
2. **No Claude Code:** registre o servidor, apontando para a pasta onde está o `oxy-mcp.exe`:

   ```
   claude mcp add oxy -- "C:\caminho\da\OXY Engine\oxy-mcp.exe"
   ```

3. **No Claude Desktop:** acrescente em `claude_desktop_config.json`:

   ```json
   {
     "mcpServers": {
       "oxy": { "command": "C:\\caminho\\da\\OXY Engine\\oxy-mcp.exe" }
     }
   }
   ```

Para compilar a partir do código-fonte, use `cargo build -p oxy_mcp --release`. O executável sai em `target/release/oxy-mcp.exe`.

## Como o agente trabalha

**Ao vivo (projeto aberto no editor).** O servidor encontra o editor aberto pelo canal local e age sobre ele:
- Cada lote de comandos aparece na hora e vira um passo no histórico, com o rótulo **Agente: …**.
- O Console mostra as ações com a origem **Agente**, e você pode desfazer tudo com Ctrl+Z.
- Quem salva é você. O agente só salva se você ligar **Permitir que agentes salvem** (veja [Salvar ao vivo](#salvar-ao-vivo)). A importação, como o **Importar** da Biblioteca, e os comandos de pastas e arquivos (mover, renomear, excluir) mexem nos arquivos da pasta do projeto na hora, num passo que o Ctrl+Z desfaz com os arquivos; o arquivo do projeto só muda quando o projeto é salvo (veja [Pastas do projeto](#pastas-do-projeto)).
- O agente lê o Console e sabe se você está testando o jogo, para entender o que deu errado no seu teste. Ele também pode testar o jogo no editor enquanto você assiste (veja [Teste ao vivo pelo agente](#teste-ao-vivo-pelo-agente)).
- Se você estiver arrastando ou digitando, o pedido espera o gesto terminar.
- Durante um teste do jogo, uma operação de modelagem em prévia ou uma pose provisória da animação, o editor recusa a edição e explica o motivo.
- A exceção são os scripts: eles são arquivos `.luau` de qualquer pasta do projeto, e o agente os grava no disco na hora, também ao vivo e durante um teste, que recarrega o que mudou. O Ctrl+Z da OXY não desfaz essas gravações (veja [Scripts com o agente](#scripts-com-o-agente)).

**Arquivos (sem editor aberto).** Com o caminho do projeto, o agente edita os arquivos diretamente:
- Antes da primeira gravação de cada sessão do servidor (cada vez que o cliente MCP inicia o `oxy-mcp`), o arquivo do projeto é copiado para `.oxy/agente/project.oxy.json.bak`, e cada arquivo de modelo que a gravação muda, para `.oxy/agente/<caminho>.bak` (`.oxy/agente/Pista/Torre.modelo.json.bak`), como os scripts. As gravações seguintes da mesma sessão não mexem nessas cópias: elas guardam o projeto como estava antes de o agente começar aquela sessão, o ponto para onde dá para voltar, e não só o de antes da última chamada. Uma cópia apagada durante a sessão é guardada de novo na gravação seguinte. As respostas trazem o caminho da cópia do projeto em `previous_version` e as dos modelos em `previous_models`. Até a 0.6, a cópia do projeto ficava ao lado dele, em `project.oxy.json.agente.bak`; uma que tenha ficado ali pode ser apagada.
- As cópias ficam em `.oxy/`, fora da Biblioteca: nem a exportação do jogo nem os pacotes da engine as levam. Num projeto seu com controle de versão, ignore a pasta `.oxy/` (travas, cópias, lixeira e backups da própria OXY).
- Um projeto do layout antigo (imagens e sons como `assets/<id>`, modelos dentro do `project.oxy.json`, como a 0.6 e as versões de desenvolvimento da 0.7 gravavam) é organizado em pastas na primeira gravação do agente nos arquivos (`oxy_apply` ou `oxy_import`; um lote com comandos de pastas, um `save_model` com `folder`, renomear ou excluir um script e um `oxy_import` com `folder` o organizam antes de aplicar, porque precisam das pastas), como no primeiro Salvar do editor: cada imagem vai para `Imagens/`, cada som para `Sons/` e cada modelo para `Modelos/<Nome>.modelo.json`, com o nome que aparece na Biblioteca (um nome que o Windows não aceita é ajustado, e o segundo de um tipo com o mesmo nome vira "Música 2"); os scripts ficam onde estão e nenhum ID muda. Antes, uma cópia completa do projeto como estava vai para `.oxy/backup/antes-das-pastas-<data>/`, que ainda abre na versão que o fez. A resposta traz `converted` (`summary`, `moved`, `models`, `backup` e, quando algum nome mudou, `notes`), e o editor mostra o mesmo resumo no Console quando abre o projeto. Uma organização interrompida (computador desligado, por exemplo) é terminada ou desfeita na abertura seguinte. Logo depois de organizar, os scripts do projeto são conferidos: um som ou modelo que um script cita pelo nome e cujo nome a organização ajustou vem nos avisos com a linha e o nome novo (`scripts/sons.luau:3: audio.play: o som "Pulo: alto" agora se chama Pulo alto; atualize o script, que no jogo para com erro nessa linha`), e o editor mostra o mesmo no Console. Um projeto salvo numa pasta com imagens, sons ou modelos que ele não usa continua no layout antigo, e o aviso diz quais arquivos são.
- Um projeto de formato anterior (de uma OXY mais antiga) é salvo no formato 6 já na primeira edição. Além da cópia em `.oxy/agente/`, fica um backup permanente do arquivo como estava antes da conversão: a cópia completa em `.oxy/backup/antes-das-pastas-<data>/` quando a gravação o organiza em pastas, ou `project.oxy.json.schema-5.….backup.json` ao lado dele quando ele continua no layout antigo. Depois disso, a 0.6.x e versões anteriores não abrem mais o projeto (a cópia completa abre).
- Se o mesmo projeto estiver aberto num editor, o servidor sempre usa o editor, para não haver duas versões. Com os agentes desligados nas Preferências, o editor não aparece para o servidor, mas guarda `.oxy/editor.lock` enquanto o projeto está aberto: nos arquivos, o agente lê o projeto e não grava (`oxy_apply`, `oxy_import` e as ações `write`, `rename`, `delete` e `vscode` do `oxy_scripts` recusam até a pessoa ligar os agentes ou fechar o projeto; as ferramentas de arquivo do próprio agente não passam pela trava). Cada gravação do agente segura `.oxy/agente.lock`, que o editor espera ao abrir e ao salvar o projeto.
- O projeto abre como no editor: um arquivo de imagem, som ou modelo que sumiu, que não pode ser lido agora ou cujo caminho salvo é inválido não impede de abrir; a resposta traz o que a abertura disse em `open_warnings` (o recurso fica com o problema, e jogar e exportar recusam enquanto ele for usado). Num projeto em pastas (formato 6, `"layout": "Tree"`), cada modelo é um arquivo `<Nome>.modelo.json`, um modelo movido ou renomeado fora da OXY é achado pelo ID que tem dentro, e um arquivo novo de tipo conhecido entra no projeto com o nome do arquivo; a próxima gravação guarda isso.
- Os caminhos das respostas (`saved`, `previous_version`, o `folder` do `oxy_new_project` e do `oxy_export`) saem com um tipo só de barra, a do Windows, mesmo quando `project`, `folder` ou `destination` vêm com `/`. Antes, saíam misturados, como `C:/Users/…/probe\project.oxy.json`.

**Atomicidade.** Os lotes valem por inteiro: se um comando falha, nada muda, e a mensagem diz qual comando falhou e por quê. As regras são as mesmas do editor, porque a validação é a mesma de salvar. O comando é contado do 0, como em `"$N"` e em `created`, e a posição vem também por extenso: `Comando 1 (set_node_params, o 2º do lote): Nó … não existe neste objeto. Nada foi alterado.` Na 0.5.0, a mensagem contava do 1 e dizia `Comando 2`. Os erros de leitura dos comandos também vêm em português, como ``valor `Parkour` desconhecido; os aceitos são `direct`, `parkour`, `chained` (maiúsculas e minúsculas contam: escreva `parkour`)``, `falta o campo …`, `tipo errado: recebeu uma lista, esperava um objeto` e `tamanho errado: 2 itens, esperava uma lista de 3 itens` (uma `position` com dois números). Um tipo que a tradução não conhece aparece com o nome em inglês, como o leitor de JSON o escreve.

## Ferramentas

| Ferramenta | O que faz |
| --- | --- |
| `oxy_status` | A versão e a identidade do servidor, os editores abertos com agentes permitidos, projeto (com o layout e como estão os scripts), cena ativa, alterações não salvas, desfazer/refazer, se há um teste do jogo rodando e quem joga, e se o agente pode salvar |
| `oxy_new_project` | Cria um projeto novo, como o **Novo projeto** do editor, numa pasta nova ou vazia que você indicar; sempre nos arquivos, sem passar pelo editor |
| `oxy_project` | Cenas (com o fundo de cada uma), recursos (com o arquivo, como cada um está no disco, quem usa cada um e, nos modelos, a raiz e as peças), as pastas e os scripts do projeto, ações de entrada (com a tecla e quem usa cada uma), superfícies físicas, variáveis do jogo (com o valor inicial e quem usa cada uma), nomes dos grupos de colisão e como o jogo exportado abre (título, janela e tela cheia); ou o que uma pasta tem |
| `oxy_scene` | Árvore de objetos da cena e o fundo dela, com componentes, tamanho da lógica e os scripts de cada objeto; sob pedido, posição no mundo, tamanhos e caixas, e leitura por partes |
| `oxy_entity` | Um ou vários objetos, inteiros ou só as partes pedidas, com a posição no mundo, as caixas, a lógica resumida com os nomes do que os nós usam, os scripts que o objeto roda (com os eventos, os atributos e a memória de cada um, e os eventos que nunca rodam nele), os componentes que ainda podem receber e quem aponta para o objeto |
| `oxy_find` | Busca objetos pelo nome em todas as cenas, por páginas |
| `oxy_catalog` | A API dos scripts em Luau (os nomes de cada área, ou a assinatura e a ajuda das funções pedidas), componentes, formas, presets (o que cada um cria e as opções), perfis de movimento (com os valores) e as teclas que as ações de entrada aceitam; os nós da lógica, que são legado, só quando pedidos |
| `oxy_apply` | Aplica um lote de comandos (criar, transformar, componentes, ajuste dos colisores, atributos, nós, ligações, organização da lógica, scripts e tirar a lógica de nós, ações de entrada, superfícies físicas, variáveis do jogo, fundo das cenas, jogo exportado, modelos, cópias entre cenas, animações, perfis de movimento…) |
| `oxy_import` | Importa imagens PNG e sons WAV como recursos do projeto, um arquivo ou vários de uma vez, na pasta que o agente escolher, e, se pedido, já aplica a imagem num objeto |
| `oxy_scripts` | Lista (com quem roda cada um), lê, confere, grava, renomeia, move e exclui os scripts em Luau do projeto, em qualquer pasta, e prepara o VS Code com a extensão luau-lsp |
| `oxy_export` | Exporta o jogo como o **Exportar jogo** do editor, para a pasta que você indicar, e confere o jogo exportado |
| `oxy_validate` | Valida o projeto com as regras de salvar e avisa o que o jogo ignoraria ou o que nele pararia com erro, inclusive arquivos de recursos que faltam ou não servem |
| `oxy_simulate` | Roda o jogo sem janela numa cópia do projeto, com entradas programadas, um bot que leva um personagem por um caminho, preparação e condições de parada, e relata trocas de cena, logs, ações, sons, eventos de movimento e áreas, a pausa do jogo, a câmera, a interface do jogo, os objetos observados, as variáveis do jogo, o que toca, os erros e o custo dos scripts e o resumo do estado no fim; se pedido, confere que o teste se repete e que nenhum script guarda estado escondido |
| `oxy_screenshot` | Imagem da vista do editor (ao vivo), da câmera do jogo com a interface do jogo, de uma câmera livre ou de cima e de lado, com os colisores quando pedido |
| `oxy_select`, `oxy_frame` | Ao vivo: seleciona e enquadra objetos para você ver do que o agente fala |
| `oxy_undo`, `oxy_redo` | Ao vivo: desfaz ou refaz o último passo |
| `oxy_console` | Ao vivo: as linhas do Console (editor, agente, jogo e lógica), com o arquivo e a linha do script de onde a linha veio, só as novas quando o agente pede |
| `oxy_play` | Ao vivo: inicia, pausa, retoma e para um teste do jogo no editor e manda entradas a ele, sem tomar o seu mouse nem o teclado |
| `oxy_save` | Ao vivo: salva o projeto, só quando você permite em **Preferências do editor** |

As descrições das ferramentas estão em inglês, para os agentes. As mensagens e erros do editor continuam em português.

## Leituras compactas

Os clientes MCP cortam respostas longas, e cada caractere ocupa o contexto do agente. Por isso:
- As respostas vêm em JSON compacto, sem espaços, com os números arredondados em 4 casas decimais (`0.4000000059604645` vira `0.4`). Abaixo de 1, guardam 4 algarismos significativos, para que um valor pequeno volte como foi posto (`0.00015` continua `0.00015`) e possa ser escrito de novo sem mudar. Valores menores que 0,00001 viram 0: é o ruído das contas em f32, como o que um grupo girado 90° deixa nas posições dos filhos no mundo.
- Ao vivo e nos arquivos, as leituras aceitam as mesmas opções e dão a mesma resposta: o editor responde pela mesma função do núcleo que o servidor usa nos arquivos.
- Opções inválidas são recusadas antes de o servidor procurar o editor ou o projeto, com o nome da opção na mensagem. Uma opção que a ferramenta não conhece é ignorada; no `oxy_entity` e no `oxy_simulate`, a resposta a lista em `unknown_options`, com a opção mais parecida, como `fieldz: opção desconhecida, ignorada; quis dizer fields?`. Antes, ela era ignorada em silêncio, e um `check_vm_reset` escrito errado parecia ter rodado.
- **Cenas pelo nome:** o `scene` de todas as ferramentas (`oxy_scene`, `oxy_entity`, `oxy_apply`, `oxy_import`, `oxy_select`, `oxy_simulate`, `oxy_screenshot`, `oxy_play`) aceita o ID ou o nome da cena, sem diferenciar maiúsculas, como o `oxy_project` a mostra em `scenes`. Um nome que duas cenas têm é recusado, e uma cena que o projeto não tem também, com o que o parâmetro recebeu e a lista das cenas: `scene recebeu "Fase 9", que não é o ID nem o nome de uma cena do projeto. Cenas: [{"id":"…","name":"Menu"}, …]`. Antes, só o ID valia, e o erro era `Cena Menu não existe`.
- **Objetos pelo nome:** o `id` e os `ids` do `oxy_entity`, o `root` do `oxy_scene`, o `target` e os `ids` do `oxy_screenshot` e, no `oxy_simulate` e no `oxy_screenshot`, o `click` das entradas, o personagem do `bot`, o `object` e o `wait_for.object` dos pontos dele, o `watch`, o `spawn` e os objetos do `until` (`attribute.entity`, o valor de um atributo de objeto, `entity_absent` e `event.object`) e, nos comandos do `oxy_apply` e do `setup`, o `entity`, os `ids` e o `parent` (menos nos comandos de nós, que são legado e pedem o ID) aceitam o ID ou o nome do objeto, sem diferenciar maiúsculas nem os espaços em volta (e `"$N"` do `setup`, onde há `setup`). O nome é procurado onde o campo procura o objeto: no projeto inteiro, na cena lida (`oxy_entity`, `oxy_scene`, `oxy_screenshot`), na cena inicial (`spawn`, `entity_absent`), na cena do comando (o `parent` do `copy_entities`, na `to_scene`) ou na cena do personagem (os pontos do bot). Um nome que dois objetos têm é recusado com os IDs deles e onde cada um está, como `id: há 12 objetos chamados "Gatilho" na cena Pista; use o ID: … (em Ladrilho 1), …`; um que nenhum objeto tem também: `bot: "Jogadr" não é o ID nem o nome de um objeto do projeto`. Antes, só o `click` aceitava o nome, e os outros diziam que um objeto com esse nome não existia. Até a 0.6, os comandos pediam o ID do objeto.

**Árvore da cena** (`oxy_scene`):
- A resposta traz o tipo da cena (`kind`) e o fundo dela (`background`), na forma que o `set_scene_background` recebe: `"sky"` (o Céu da OXY) ou `{"color": [r, g, b, a]}`. Uma cena sem fundo próprio, como as feitas antes de a cena ter fundo, mostra a cor escura em que ela aparece, `{"color": [0.068, 0.068, 0.072, 1.0]}`.
- `fields` acrescenta a cada objeto:
  - `world_position`: onde a posição do objeto (o pivô) fica no mundo. É o que conta para medir distâncias entre peças de grupos diferentes;
  - `rotation` (local, em graus, como o `set_transform` recebe), `scale` (local) e `dimensions` (da forma);
  - `visual_bounds`: a caixa `{min, max}` no mundo do que o objeto e os filhos mostram, inclusive peças ocultas;
  - `collider_bounds`: a caixa `{min, max, center}` no mundo do colisor que o jogo usa (o corpo do personagem 3D, o colisor 3D ou o colisor de caixa), com `sensor: true` nas áreas e `enabled: false` quando está desligado;
  - `bounds`: as duas caixas.
- Cada objeto traz `logic_nodes`, quantos nós a lógica dele tem, e `scripts`, os scripts em Luau que ele roda, pelo caminho (`["Pista/checkpoint.luau"]`), quando tem.
- `root` lista os filhos de um objeto (pelo ID ou pelo nome) em vez dos objetos da raiz da cena, e a resposta o identifica em `root`.
- `depth` limita os níveis de filhos; abaixo dele, cada objeto só diz quantos filhos tem (`children_count`).
- `limit` (100 por padrão) é o máximo de objetos na resposta, contando os filhos. `offset` e `limit` leem os objetos listados por partes: a resposta traz `total` e, quando há mais, `next_offset`. Os filhos entram nível a nível enquanto cabem; um objeto cujos filhos já não cabem só diz quantos tem (`children_count`), e a resposta traz `truncated: true`. Para ler esses filhos, use `root` com o ID do objeto.

**Objetos** (`oxy_entity`):
- `id` lê um objeto da cena, pelo ID ou pelo nome; `ids` lê vários, devolvidos em `objects`.
- A resposta é a forma de documento do objeto, sem as partes vazias (nulas), mais `world` (posição, rotação em graus e escala no mundo), `visual_bounds` e `collider_bounds` como na árvore, os componentes e os que ainda pode receber.
- A rotação no mundo (`world.rotation_degrees`) se lê como a do `set_transform`. Num objeto da raiz, é a própria `rotation_degrees`. Sob um grupo, a mesma rotação pode ser escrita com dois trios de ângulos, como `[0, 120, 0]` e `[180, 60, 180]`; vem o mais próximo da rotação do próprio objeto, entre -180 e 180. Assim, uma peça girada 120° junto com o grupo lê `[0, 120, 0]`, e não parece de cabeça para baixo.
- `fields` corta a resposta nas partes pedidas, além do ID e do nome, como `character3d.actions`, `transform.position` ou `graph.edges`. Uma parte que não existe vem `null`. Os nomes dos componentes, como o `oxy_scene` e o catálogo os dão, valem pela parte do documento que os guarda: `collider3d` e `sensor3d` leem `physics3d`, `character` lê `character3d`, `camera_control` lê `camera_rig`, `collider2d` e `sensor2d` leem `collider`, e `controller2d` lê `controller`. Antes, eram recusados como campos desconhecidos.
- A lógica vem resumida: `nodes` liga o rótulo de cada nó ao ID dele e aos parâmetros que fogem do padrão, e `edges` traz as ligações em texto, como `event.input(Reiniciar).exec -> character.teleport.exec`.
  - O rótulo é a operação e, entre parênteses, o parâmetro principal, pelo nome do que ele aponta: a cena, o som, a animação, a ação de entrada, a variável do jogo ou a superfície (`action.scene(Menu)`, `event.input(Reiniciar)`, `action.animation(Giro)`). Quando o nó aponta um objeto pelo parâmetro (o `target`, por exemplo), o nome do objeto vem depois de uma seta: `action.component(visible → Resultado)`, `camera.mode(fixed → Câmera principal)`. Antes, o rótulo trazia o ID truncado de ações de entrada e animações e não dizia o objeto.
  - Um parâmetro cuja entrada de mesmo nome está ligada fica fora do rótulo, porque o jogo usa a entrada: um `condition.branch` com a condição ligada é `condition.branch`, e não `condition.branch(true)`.
  - Nós que teriam o mesmo rótulo ganham o primeiro parâmetro que usam cujo valor muda entre eles: `attribute.set(Aviso, value = "3")` e `attribute.set(Aviso, value = "2")`, `action.component(visible → Placa, enabled = false)`. Um rótulo que ainda se repete, como o de dois `condition.branch` com a condição ligada, termina em `#N`, a posição do nó no grafo. Antes, todo rótulo repetido terminava em `#N`, e sete `condition.branch(true)#N` não diziam qual era qual.
  - Em `params`, um valor que aponta algo do projeto traz também o nome: `{"Object": "<ID>", "name": "Resultado"}`, `{"Text": "<ID>", "name": "Menu"}`.
- `referenced_by` lista o que aponta para o objeto, na mesma cena: `{scene: {id, name}, entity, name, role}`, em que `entity` e `name` são o objeto que guarda a referência e `role` diz como: `attribute <nome>` (um atributo de objeto), `ui` (um elemento da interface mostra um atributo dele), `camera_control` (com `param` `target`, a câmera o segue, ou `hidden`, a câmera o esconde), `animation` (a animação `clip` de outro objeto o move) ou a operação de um nó da lógica, com `node` (o rótulo do nó no resumo) e `param`. As animações do próprio objeto não entram, nem um parâmetro cuja entrada está ligada, que o jogo não usa. Vêm até 50; `referenced_by_total` conta todas quando há mais. Sem nenhuma, o campo fica de fora, a menos que venha em `fields`, que o devolve como `[]`.
- Nas animações (`clips`), cada quadro-chave traz também `rotation_degrees`, a rotação em graus, como o `set_clip` recebe; a `rotation` da `transform` continua em radianos, como fica gravada. O `update_entity` recusa `rotation_degrees` nos quadros-chave, em vez de ignorá-lo: para gravar a rotação em graus, use o `set_clip`.
- Os filtros de colisão (`physics3d.filter` e `character3d.body.filter`) trazem, ao lado de `category` e `mask`, `category_groups` e `mask_groups`: os nomes dos grupos cujos bits estão ligados, ou `"all"` quando todos estão, como `{"category": 4, "mask": 2, "category_groups": ["Áreas"], "mask_groups": ["Personagens"], …}`.
- Malhas e geometria de colisão convexa ou de triângulos vêm como contagens.
- `graph: "full"` e `geometry: "full"` devolvem esses trechos como estão gravados, só com os IDs, a forma que o `update_entity` edita.
- `scripts` lista os scripts que o objeto roda, na ordem: `{path, missing?}` e, como o script carrega, `callbacks` (os eventos `on_*` que ele define), `attributes` (os nomes que `Modulo.attributes` declara), `state` (os campos de `Modulo.state`, cada um com o tipo, com os nomes do `oxy_project`: `Number`, `Text`, `Bool`, `Vector3`, `Vector2`, `Object`, `Surface` e `Table`, como `{"vezes": "Number"}`), `error` (por que ele não carrega, com o arquivo e a linha) e `warnings`, os eventos que nunca rodam naquele objeto: `on_area_enter` e `on_area_exit` num objeto sem área (`sensor3d`; numa cena 2D, `sensor2d`) e `on_click` num que não recebe cliques (nem forma nem botão da interface). `missing: true` diz que o arquivo não está na pasta do projeto.

**Busca** (`oxy_find`): devolve `{objects, total}` e `next_offset` quando há mais, com `offset` e `limit` (50 por padrão).

**Catálogo** (`oxy_catalog`): sem opções, traz a API dos scripts em resumo, em `api`: `areas` (cada área da API, como `events`, `object`, `audio`, com o título e os nomes das funções, propriedades, métodos e eventos dela), `total` e `types_file` (o arquivo de tipos que o VS Code lê), mais as partes listadas abaixo e `legacy_nodes`, que diz como pedir os nós. Para escrever um script, o agente pede o que vai usar com `api` (os nomes como os scripts os escrevem, `audio.play`, `obj.position`, `obj:after`, `obj.character:jump`, `on_area_enter`, sem diferenciar maiúsculas, ou prefixos que terminam em `.` ou `:`, como `audio.` e `obj:`) ou com `area`, e recebe só essas linhas, completas: `{name, signature, kind, area, help, writable?, names?, nodes?}`, com a assinatura como o script escreve, o tipo (`function`, `method`, `property`, `callback`, `declaration`, `constant` ou `reserved`, um nome que chega na 0.8), a ajuda em inglês, `writable` numa propriedade que o script grava, `names`, o que os textos dela nomeiam no projeto (`sound`, `variable`, `scene`…, que a conferência de nomes confere) e `nodes`, os nós legados que fazem o mesmo. `offset` e `limit` leem as linhas por partes. Um nome que a API não tem é recusado com o mais parecido: `audio.paly não é um nome da API dos scripts; quis dizer audio.play?`. A ajuda em português está nos tipos que o `oxy_scripts vscode` grava e em [API dos scripts](api-scripts.md), gerados da mesma tabela. Até a etapa 4 da 0.7, a lista da API estava na descrição do `oxy_scripts`; agora ela é do catálogo, e a descrição ficou curta.

Os nós da lógica são legado (congelados desde a 0.7: nenhum nó novo) e continuam rodando nos projetos que os têm. `nodes: true` traz os nós resumidos (operação, nome, categoria e descrição), com a lista de categorias em `categories`; antes da 0.7, era isso que o catálogo trazia sem opções. Pedir a API e os nós juntos é recusado. Para mexer na lógica de nós, o agente pede os nós que vai usar com `operations` (por exemplo `["event.input", "character."]`, em que o ponto final pega todas as operações que começam assim) ou `category`, e recebe só esses nós, com portas e parâmetros. Um parâmetro de valores fixos (o modo de uma ação de entrada, o operador de uma conta, o tipo de evento do personagem…) traz a lista em `choices`, com o valor e o nome de cada opção; um parâmetro numérico que o jogo limita traz a faixa em `min` e `max` (sem `max` quando não há limite de cima), como a busca local do `character.teleport` (de 0 a 2 m) e o volume do `action.sound` (de 0 a 1); e `ref` diz o que um parâmetro aponta: uma cena, um áudio, uma animação, um objeto, um atributo, uma ação de entrada, uma superfície, um marcador ou uma variável do jogo (`variable`). Com os dois, as operações pedidas precisam ser da categoria; uma que existe em outra categoria é recusada com o nome da categoria dela, e não como desconhecida. `brief` escolhe o formato, e `offset` e `limit` leem os nós por partes. A descrição de cada nó é só dele: diz o que o nó faz, o que cada saída significa e em que unidade (metros, m/s, graus e segundos; rotações e o olhar da câmera vêm em graus). Antes, famílias inteiras, como `camera.*`, `character.*`, `query.*`, os vetores e as superfícies, repetiam uma descrição só, sem unidades.

**Quando os dados são lidos.** Um nó de dados (sem entrada de execução, como `attribute.get`, `variable.get` ou `math.binary`) é calculado quando o nó que usa a saída dele executa, a cada vez, e não uma vez por evento: uma cadeia de dados ligada a dois nós é calculada duas vezes e, depois de uma ação mudar o que ela lê, dá o valor novo. Assim, `attribute.get(Tempo)` mais `dt` ligado a `attribute.set(Tempo)` e depois a `text.time` soma `dt` duas vezes. Para usar um valor logo depois de gravá-lo, leia-o com outro `attribute.get` ou `variable.get`, em vez de reaproveitar a conta que o calculou. Eventos e ações guardam as saídas uma vez por execução (o tempo do `event.step`, o valor do `random.number`, o contato de um `query.*`, o sucesso do `character.teleport`, o objeto criado pelo `action.spawn`): os nós seguintes do mesmo fluxo leem esses valores guardados. O `value_format` do catálogo diz o mesmo, em inglês.

Sem opções, o catálogo traz também:
- `input_keys`: as teclas que as ações de entrada aceitam;
- `surface_presets`: os presets de superfície;
- `presets`: cada preset do `create_entity` com `id`, `description` (para que serve: `platform` é uma plataforma móvel, e não um personagem de jogo de plataforma), `creates` (as peças que ele cria, na ordem em que o lote as devolve, com a forma, os componentes, o pai e as animações) e `params` (as opções, com o valor padrão);
- `ui_elements`: os tipos de elemento da interface do jogo (`kinds`: `Text`, `Image`, `Button` e `Bar`) e, em `fields`, os campos do `ui` de um objeto, que o `update_entity` edita, entre eles o alinhamento e o tamanho do texto (veja **Interface do jogo**, nos comandos);
- `movement_profiles`: os perfis Direto, Ágil com embalo e Saltos encadeados, com `id` (`direct`, `parkour` ou `chained`), `label` e `values`, os 14 valores que o perfil escreve no personagem. Ágil com embalo se chamava Parkour; só o nome mudou, e o `id` continua `parkour`, nos comandos, no nó `character.profile` e nos projetos já salvos.

**Projeto** (`oxy_project`):
- `scenes`: cada cena com `id`, `name`, `kind` (`2d` ou `3d`), `objects` (quantos objetos tem) e `background`, o fundo, como no `oxy_scene`.
- `input_actions`: cada ação de entrada com `id`, `name`, `key` e `used_by`, os objetos que a usam (`{entity, name, role}`, em que `role` é o componente, como `character` ou `controller2d`, ou a operação do nó, como `event.input`). Quando outra ação usa a mesma tecla, `shares_key_with` lista essas ações (`{id, name}`): no jogo, a tecla dispara todas.
- `surfaces`: cada superfície física com os valores dela (`friction`, `traction`, `speed_multiplier`, `conveyor`, `conveyor_space`) e `used_by`, como nas ações (`role` `collider3d`, `character`, a operação do nó ou `attribute <nome>`).
- `variables`: cada variável do jogo com `id`, `name`, `type` (`Number`, `Text`, `Bool`, `Vector2` ou `Vector3`), `value` (o valor inicial, com o tipo, como `{"Number": 0}`), `persistent` (marcada para ser salva entre partidas) e `used_by`, como nas ações (`role` `variable.get` ou `variable.set`).
- `assets`: cada recurso com `id`, `name`, `kind` (`Texture`, `Audio` ou `Model`), `path` (o arquivo, relativo à pasta do projeto, `Pista/Checkpoint.modelo.json` inclusive; só os modelos de um projeto antigo, que ficam dentro do arquivo do projeto, não têm `path`), `state` quando o arquivo não está bem (`missing`: não está na pasta do projeto; `unreadable`: não pôde ser lido agora; `invalid_path`: o caminho salvo é inválido; `error`: o conteúdo não serve, ou o modelo está indisponível; `unsaved`: o arquivo nasce no próximo salvamento, como o de um modelo salvo ao vivo), com o motivo em `problem`, e `used_by`, como nas ações (`role` `material`, `ui` para a imagem de um elemento da interface, `model` para um modelo colocado, ou a operação do nó, como `action.sound`). Um modelo lista cada colocação uma vez, pela raiz, e não cada peça colocada.
- Um modelo traz também `part_count`, quantas peças tem, e `root` (`{id, name}`), a raiz: o `name` dela é o nome que o `place_model` dá à raiz colocada quando não recebe `name`, o nome que o objeto tinha ao ser salvo (como `Checkpoint 1`), que pode ser outro que o do modelo.
- `model` (o ID ou o nome de um modelo, sem diferenciar maiúsculas) troca o resumo pelas peças desse modelo: `{id, name, root, parts, total}`, cada peça como `{id, name, parent, kind}`, em que `parent` é o ID da peça mãe (`null` na raiz) e `kind` é o tipo, como no `oxy_scene`. Cada peça vem antes das filhas. `offset` e `limit` (100 por padrão) leem as peças por partes, com `next_offset` quando há mais. Os IDs das peças são os que o `"$N@<ID>"` aceita depois de um `place_model` (veja **Cópias no mesmo lote**). Um modelo que não existe é recusado com a lista dos modelos.
- Um objeto que só existe dentro de um modelo vem em `used_by` com `model`, o nome do modelo: o `oxy_entity` e o `oxy_find` não chegam a ele, que aparece nas cenas onde o modelo for colocado.
- Depois dos objetos, o `used_by` de recursos, ações de entrada, superfícies e variáveis traz as linhas dos scripts que os nomeiam com um texto literal: `{script, line, role}`, como `{"script": "Pista/checkpoint.luau", "line": 19, "role": "audio.play"}`. Um som que só um script toca aparece em uso, e o `used_by_count` da lista de uma pasta também conta essas linhas. Antes, ele aparecia sem uso, e um agente que limpava os recursos "sem uso" quebrava o script.
- `used_by` lista até 10 usos; quando há mais, `used_by_total` diz quantos são.
- `layout`: `tree` (o projeto em pastas: a pasta do projeto é a Biblioteca) ou `legacy` (um projeto antigo, com os recursos em `assets/`), com `conversion_pending: true` quando ele ainda espera ser organizado em pastas: ao vivo, quem o organiza é o próximo salvamento da pessoa (ou o `oxy_save`), e até lá os comandos de pastas são recusados; nos arquivos, a próxima gravação do agente.
- `folders` (num projeto em pastas): cada pasta do projeto, na ordem da árvore, `{path, items}`, em que `items` conta o que a Biblioteca mostra direto nela (subpastas, imagens, sons, modelos e scripts). `offset` e `limit` (100 por padrão) leem as pastas por partes, com `folders_total` e `folders_next_offset`.
- `scripts`: cada arquivo `.luau` do projeto, `{path, used_by}`, com os objetos que o anexam (`role` `script`).
- `folder` (o caminho de uma pasta, sem diferenciar maiúsculas; `""` é a raiz) troca o resumo pelo que a pasta tem, como a lista da Biblioteca: `{folder, items, total, next_offset?, other_files?}`. Cada item é `{kind, name, path}`, com `kind` `Folder` (e `items`, quantos itens a subpasta tem), `Texture`, `Audio`, `Model` ou `Script`; um recurso traz também `id`, `used_by_count` e `state`/`problem` como acima, e um script, `used_by_count`. As pastas vêm primeiro, depois os arquivos, na ordem da árvore; um recurso cujo arquivo sumiu aparece na pasta do caminho dele, com `state: "missing"`. `kind` deixa só os arquivos de um tipo, e `offset` e `limit` leem a lista por partes. `other_files` conta os arquivos que a OXY não usa (um `.txt`, um `.psd`), que a Biblioteca esconde. Uma pasta que o projeto não tem é recusada com a lista das pastas.
- `collision_groups`: os nomes dos grupos de colisão, `{bit, name}`, em que `bit` é o bit da categoria e da máscara dos colisores. Vêm os três grupos com nome padrão e os que o projeto nomeou; os outros se chamam `Grupo N`, com N = bit + 1. Os nomes se mudam no editor; os filtros de colisão os aceitam no lugar dos bits (veja **Colisores**, nos comandos).
- `game`: como o jogo exportado abre, `{title, window, fullscreen}`. `title` é o nome do jogo, que dá nome à janela, à pasta e ao executável: o título próprio ou, sem ele, o nome do projeto. `window` é `[largura, altura]` da área do jogo e `fullscreen` diz se o jogo abre em tela cheia. Muda com o `set_game_settings` (veja **Jogo exportado**, abaixo).

**Mudanças em relação à 0.5.0:** o `oxy_find` devolve `{objects, total}` em vez de uma lista; o `oxy_entity` resume a lógica e a geometria e deixa de fora as partes vazias; o `oxy_catalog` resume os nós quando não recebe opções e descreve os presets (`presets` passou de uma lista de nomes para uma lista de objetos, com o nome em `id`) e os campos da interface (`ui_elements` passou de uma lista de tipos para `{kinds, fields}`, com os tipos em `kinds`); o `oxy_scene` devolve até 100 objetos por vez, contando os filhos; e o `oxy_project` lista as ações de entrada como `[{id, name, key, used_by}]`, em vez de um mapa de ID para tecla.

## Comandos do `oxy_apply`

**Resposta.** O lote responde `{created, warnings}`:
- `created` liga o índice de cada comando que criou algo (contando do 0) aos IDs criados, na ordem, com o nome de cada um: `{"0": [{"id": "…", "name": "Porta"}]}`. O nome de um nó é a operação dele. O que um comando seguinte do mesmo lote apagou continua com o nome que tinha ao ser criado; antes, vinha `null`. Os comandos que não criam nada ficam de fora. As chaves vêm na ordem dos comandos (`"2"` antes de `"10"`); antes, vinham em ordem de texto (`"0"`, `"1"`, `"10"`, `"11"`, …, `"2"`). Vale para todo objeto de uma resposta cujas chaves são só números.
- `warnings` só aparece quando o lote deixa algo que o projeto salva, mas que o jogo vai ignorar ou em que vai parar com erro: um nó que usa uma ação de entrada que o projeto não tem (ou que guarda o nome dela, e não o ID), uma tecla que o jogo não lê, um parâmetro com valor fora das opções ou um número fora da faixa do parâmetro (veja **Faixas de números**). Um valor vazio também está fora das opções; a exceção é o modo vazio de um nó de ação de entrada, que o jogo lê como "pressionar". Avisa também de um `action.component` cujo alvo, escolhido no parâmetro `target` (e não por uma porta), não tem o que o nó liga e desliga, como uma plataforma móvel num objeto sem ela, e de um `variable.set` cujo parâmetro `value` (sem a entrada ligada) não é do tipo da variável: no jogo, esses nós param com erro. Vêm só os avisos que o lote criou, tanto ao vivo quanto nos arquivos (um lote vazio responde `{"created": {}}`); o `oxy_validate` lista todos os do projeto.
- O lote também avisa quando deixa duas ações de entrada atendendo pelo mesmo nome ou na mesma tecla (veja abaixo). O jogo distingue os nomes, e há projetos que repetem um nome ou uma tecla de propósito (um rótulo para as teclas 1, 2 e 3; pular e confirmar no Espaço), então o `oxy_validate` não lista esses avisos. O aviso vem só do lote que junta uma ação ao nome ou à tecla: excluir uma de três ações na mesma tecla, ou levá-la para uma tecla livre, não avisa sobre as duas que ficam.
- E avisa o que os comandos deixaram e o jogo leva de outro jeito, com o comando que o deixou (`Comando 2 (update_entity, o 3º do lote): …`): um colisor de caixa que ficou com a forma antiga do objeto, um colisor convexo ou de malha feito com a forma antiga (veja **Colisores**) e nós copiados para outra cena que ainda abrem ou nomeiam a cena de onde vieram. Avisa também dos fios longos que o `arrange_logic` deixou, que não mudam o jogo mas dificultam ler a lógica (veja **Lógica organizada**). Esses avisos olham o lote já terminado: se um comando seguinte resolve, o aviso não vem.
- Nos arquivos, a resposta traz também `saved` e `previous_version`.

**IDs criados no mesmo lote.** Num comando, um texto que é inteiro `"$N"` vale o primeiro ID criado pelo comando N, e `"$N.M"`, o M-ésimo (os dois contam do 0):
- Um preset devolve todas as peças, a raiz primeiro: com o comando 0 criando um jogador em primeira pessoa, `"$0"` é o jogador e `"$0.2"`, a câmera.
- `duplicate_entities` devolve uma cópia por objeto, na ordem: `"$3.1"` é a segunda cópia. Com `count`, devolve todas as cópias, uma rodada depois da outra.
- `place_model` devolve todas as peças do modelo colocado, a raiz primeiro; `copy_entities`, uma cópia por objeto; `set_clip`, o ID da animação nova; `save_model`, o ID do modelo (com `replace`, o do modelo substituído, que não muda); `arrange_logic` com `split_shared_data`, as cópias dos nós de dados.
- Os marcadores valem em qualquer lugar do comando, inclusive dentro do `patch` do `update_entity` e dos `params` dos nós.
- Só o texto inteiro conta: `"$10 de bônus"` continua sendo texto. Para escrever o próprio texto `"$5"`, use `"$$5"`.
- Um marcador que não aponta para um ID criado antes no lote é recusado, com a dica do `$$`.
- Um comando sem `scene` cujo `entity` (ou, sem ele, o primeiro de `ids`, ou o `parent`) é o marcador de um objeto criado ou copiado antes no lote usa a cena desse objeto, e não a cena padrão do lote. Assim, depois de `{"op": "create_entity", "scene": "Pista", …}` como comando 4, `{"op": "add_node", "entity": "$4", …}` sem `scene` põe o nó no objeto da Pista. O `parent` do `copy_entities` não conta, porque fica na cena de destino. Um `scene` dado no comando (ou pelo `scene` da ferramenta) vale mais que o do marcador.
- Um objeto que a cena do comando não tem é recusado com o nome da cena usada e, quando outra cena tem o objeto, com o nome dela: `Comando 8 (add_node, o 9º do lote): Controle da corrida não existe na cena Menu (a do comando); ele está na cena Pista: passe scene`. Um ID que nenhuma cena tem diz isso: `Objeto … não existe na cena Menu (a do comando) nem em outra cena do projeto`. Um nome que só um objeto de outra cena tem é recusado do mesmo jeito, com a cena dele, e um que objetos de outras cenas dividem, com os IDs e as cenas deles. Um nome dado a um comando de nós, que pede o ID, diz isso, com o objeto da cena do comando ou, quando ela não tem um, o de outra cena: `Controle da corrida é o nome de um objeto da cena Pista, e não da Menu (a do comando); os comandos de nós (legado) pedem o ID dele (…) e a cena dele em scene`. Antes, a mensagem era `Objeto <ID> não existe nesta cena`, sem dizer qual cena nem onde o objeto estava.

**Cópias no mesmo lote.** `"$N@<ID>"` vale a cópia que o comando N fez do objeto, do nó ou da animação `<ID>` do original, e `"$N.M@<ID>"`, a cópia que está junto do M-ésimo ID criado por ele. Assim, a lógica e as peças de uma cópia se editam no mesmo lote que a fez:
- Vale para os comandos que copiam objetos: `duplicate_entities`, `copy_entities`, `save_model` (a cópia que fica no modelo), `place_model` e `duplicate_scene`. Em `{"op": "duplicate_entities", "ids": ["$0"], "count": 3}` como comando 5, `"$5.1@<nó>"` é aquele nó na segunda cópia e `"$5.1@<peça>"`, aquela peça dentro dela; `"$5@<ID>"` fica na primeira.
- O `<ID>` é o do original: um ID que você leu ou um marcador `"$K"` ou `"$K.M"` de um objeto ou nó criado antes no lote, como em `{"op": "set_node_params", "entity": "$5.1", "node": "$5.1@$3", "params": {…}}`. No `place_model`, é o ID da peça, do nó ou da animação como o modelo os guarda: o `oxy_project` com `model` lista as peças com os IDs delas (`"$4@<ID da peça>"` é aquela peça na cópia colocada pelo comando 4); quando o modelo é salvo no mesmo lote, os marcadores se encadeiam: com o `save_model` como comando 3 e o `place_model` como comando 4, `"$4@$3@<ID do nó na cena>"` é aquele nó na cópia colocada. No `duplicate_scene`, `"$N@<ID da cena>"` é a cena nova, como `"$N"`.
- Um original que o comando não copiou é recusado, com o objeto, o nó ou a animação que tem esse ID: `"$5@<ID>": o objeto Outro (<ID>) não está entre o que o comando 5 (duplicate_entities, o 6º do lote) copiou`. Também é recusado o marcador de um comando que não copia objetos ou de uma cópia que ele não fez.
- Para o próprio texto, `"$$5@x"` vale `"$5@x"`. Antes, um texto como `"$5@x"` não era marcador e ficava como estava.

**Lógica organizada.** Os nós criados sem `position` pelo `add_node` ganham lugar quando o lote termina, junto com os outros criados assim no mesmo lote, para que a lógica fique legível no editor. Os nós de antes do lote e os que recebem `position` ficam onde estão.
- Os eventos ficam na primeira coluna e a execução segue da esquerda para a direita, uma coluna por passo, pelo caminho mais longo; um nó que só fornece ou recebe dados fica uma coluna à esquerda do primeiro nó que o usa. Na coluna, os nós se empilham na ordem do que os alimenta, e cada evento tem a sua faixa, uma abaixo da outra. Os retângulos dos nós, do tamanho que o editor desenha, nunca se sobrepõem.
- Nós novos ligados a nós que ficam começam à direita deles (ou terminam à esquerda, quando só os alimentam), descendo se o lugar está ocupado; os outros vão para baixo da lógica que já existe.
- Antes de `duplicate_entities`, `copy_entities`, `save_model` e `duplicate_scene`, os nós sem posição já ganham lugar: as cópias levam a lógica organizada.
- `arrange_logic {entity, nodes?, split_shared_data?}` organiza do mesmo jeito os nós de `nodes`, ou todos, quando `nodes` não vem; os outros ficam onde estão. Ao vivo, é um passo de desfazer, como os outros lotes (**Agente: Organizar lógica**). Um objeto sem lógica e um nó que o objeto não tem são recusados.
- Cada evento tem a sua faixa: os nós que a execução dele alcança (um nó que dois eventos alcançam fica na faixa do primeiro, na ordem do grafo; a execução que nenhum evento alcança forma mais uma faixa). Um nó de dados usado em várias faixas, como um `attribute.get(Jogador local)` que alimenta quatro `Se / Senão`, puxa fios que atravessam a lógica.
- Com `split_shared_data: true`, antes de organizar, cada faixa ganha a sua cópia desses nós de dados, com o que os alimenta, e nenhum fio passa de uma faixa para outra. Valem os nós sem portas de execução que só leem outros nós assim: constantes (`value.*`), `attribute.get`, `variable.get`, `scene.current`, `time.read`, contas e comparações sobre eles. A lista sai do catálogo (todo nó sem porta de execução), não de nomes fixos. Um nó de dados que lê um evento ou uma ação, como o objeto que entrou na área (`context`) ou o objeto criado por um `action.spawn`, fica na faixa de onde vem. A cópia leva os parâmetros e as entradas do original, que fica com a primeira faixa. O jogo calcula os nós de dados a cada leitura, sem guardar o valor e sem mudar nada (veja **Quando os dados são lidos**), então a lógica faz exatamente o que fazia. Com `nodes`, só os nós de `nodes` são copiados. As cópias vêm em `created` (o nome de cada uma é a operação), e os IDs delas saem do objeto, do original e do evento da faixa: o mesmo lote no mesmo projeto dá os mesmos IDs.
- Depois de organizar, o lote avisa dos fios que ficaram longos na vertical, os que sobem ou descem mais de 600 unidades entre as pontas (mais de meia tela do editor em 100%) e cruzam a lógica em volta, o mais alto primeiro, pelos rótulos do resumo da lógica e com a altura de cada um: `Comando 0 (arrange_logic, o 1º do lote): a lógica de Jogador ficou com 7 fios longos, …: attribute.get(Etapa).value -> condition.compare(<)#70.a (2432); …`. Um fio comprido na horizontal segue o sentido da lógica e não entra no aviso. Sem `split_shared_data`, quando algum desses fios sai de um nó de dados que a opção copiaria (com os mesmos `nodes`), o aviso a sugere e diz quais são esses nós; um fio de execução, ou de dados ligados a um evento, a opção não encurta, e o aviso não a sugere.
- Antes, cada nó sem `position` ia para a direita do mais à direita, numa fileira só.

**Ligar a lógica em menos comandos.** O `connect` aceita várias ligações num comando só, e o `add_node` liga as entradas do nó novo ao criá-lo. Uma lógica de 9 nós e 12 ligações pode cair de 21 comandos para 9.
- `{"op": "connect", "entity": "…", "links": [[from_node, from_port, to_node, to_port], …]}` liga todas, na ordem. A forma de uma ligação só (`from_node`, `from_port`, `to_node`, `to_port`) continua valendo; as duas juntas no mesmo comando são recusadas.
- `add_node` aceita `links: [[from_node, from_port, to_port], …]`: cada uma liga a saída `from_port` de um nó que o objeto já tem (pelo ID ou por `"$N"`) à entrada `to_port` do nó novo. Por exemplo, com um `event.area_enter` criado pelo comando 3, `{"op": "add_node", "entity": "$0", "operation": "action.damage", "links": [["$3", "exec", "exec"], ["$3", "context", "target"]]}` cria o dano já ligado à entrada na área e ao objeto que entrou. Para montar uma lógica, crie os nós na ordem em que a execução e os dados correm, cada um com as ligações aos de antes, e use o `connect` com `links` para o resto.
- O `disconnect` aceita as mesmas duas formas, `links` ou uma ligação só, e desliga tudo ou nada. Uma ligação que não existe é recusada com os nós pelo nome: `Ligação 1 de links (a 2ª): A saída exec de Mensagem de diagnóstico (debug.message) não está ligada à entrada exec de Esperar sem bloquear (control.wait)`. Antes, o `disconnect` aceitava só uma ligação, e o erro era `Essas portas não estão ligadas`.
- As ligações seguem as mesmas regras do `connect` e entram tudo ou nada, com o lote: uma recusada falha o comando, que diz qual foi, contando do 0 como os comandos, os nós pelo rótulo e pela operação e as portas que o nó tem: `Comando 4 (connect, o 5º do lote): Ligação 1 de links (a 2ª): O nó Ao iniciar cena (event.scene_start) não tem a saída valor; saídas: exec`. Um nó de outro objeto (`O nó … é da lógica de Outro, não da de Painel`), uma entrada de dados já ligada, tipos que não combinam e um ciclo também são recusados pelo nome; antes, o `connect` citava o ID interno do nó.

**Valores fixos.** `add_node` e `set_node_params` recusam valores fora das opções do parâmetro, como o modo `segurando` numa ação de entrada, e a mensagem lista as opções. Antes, o valor era aceito e o nó nunca disparava. O editor usa as mesmas listas.

**Faixas de números.** `add_node` e `set_node_params` recusam um número fora da faixa do parâmetro (`min` e `max` no catálogo), com o nome do nó e a faixa: `O parâmetro search (Busca local máxima (m; 0 recusa ocupado)) de Teleportar com segurança aceita números de 0 a 2; recebeu 3`. Antes, o valor era aceito, e no jogo o nó recusava em silêncio (a busca acima de 2 m devolvia `success` falso, sem log). Têm faixa os parâmetros que o jogo recusa ou limita: a busca do `character.teleport`, os volumes (de 0 a 1) e as transições (de 0 a 60 s) do som, os segundos do `control.wait` (até 86400) e das câmeras, a quantidade do `action.damage`, a semente do `random.seed`, a distância e os grupos dos `query.*`. As faixas ficam no catálogo, não no projeto, e o formato continua o 5: um projeto salvo antes abre como estava, e o `oxy_validate` avisa de cada número fora da faixa, com o objeto e o nó pelo nome, dizendo o que o jogo faz com ele: o nó recusa o valor (e para com erro, ou fornece `success` falso com o motivo) ou fica com o limite mais próximo. Um parâmetro cuja entrada de mesmo nome está ligada fica de fora, porque o jogo lê a entrada. No editor, o campo desses parâmetros só arrasta e aceita números dentro da faixa.

**Valores dos parâmetros e atributos.** Os valores levam o tipo: `{"Number": 3}`, `{"Text": "…"}`, `{"Bool": true}`, `{"Object": "<ID>"}`, `{"Vector2": [x, y]}`, `{"Vector3": [x, y, z]}`, `{"Surface": "<ID>"}`.
- Num parâmetro de nó, o valor também pode vir simples quando o catálogo dá o tipo do parâmetro e a leitura é óbvia: um número num parâmetro `Number`, um texto num `Text` e `true` ou `false` num `Bool`. Assim, `"params": {"action": "Pausar", "mode": "held"}` vale o mesmo que com `{"Text": …}`.
- Alguns parâmetros aceitam qualquer tipo: os que têm uma entrada de mesmo nome do tipo `any` no catálogo, como o `value` do `attribute.set` e o `a` e o `b` do `condition.compare`. O padrão deles é só o valor inicial, não o tipo, e um valor simples vale pela forma: um número vira `Number`, um texto vira `Text` e `true` ou `false` vira `Bool`. Assim, `{"attribute": "Checkpoint", "value": "Outro"}` guarda o texto `Outro`. Uma lista ou um objeto precisa do tipo, como `{"Vector3": [0, 1, 0]}` ou `{"Object": "<ID>"}`.
- Os outros valores simples são recusados com uma mensagem em português que diz o parâmetro e a forma esperada, como `O parâmetro target do nó action.damage precisa de um valor marcado com o tipo, como {"Object":"abc"}; recebeu "abc"`. Um texto nunca vira objeto ou superfície sozinho, e um tipo com a inicial minúscula (`{"number": 3}`) também é recusado, com o aviso de que o nome do tipo começa com maiúscula.
- Os atributos não têm tipo no catálogo: o `set_attribute` só aceita valores com o tipo, e um valor simples é recusado da mesma forma (`O atributo vida precisa de um valor marcado com o tipo, como {"Number":3}; recebeu 3`).
- Antes, todos esses casos davam o erro do leitor de JSON, em inglês, sem dizer o parâmetro.

**Fundo da cena.** `set_scene_background {scene?, background}` muda o que a cena mostra atrás dos objetos, na vista do editor, no teste, no jogo exportado e nas capturas. Sem `scene`, vale a cena da ferramenta, como nos comandos de objetos. O editor o desfaz como os outros, e no editor o mesmo fundo fica no bloco **Cena aberta** das Propriedades, sem nada selecionado.
- `"sky"` é o **Céu da OXY**, o céu de dia estilizado que vem com a engine (o céu de dia do pacote Skyboxes da Kenney, CC0): um panorama em volta da câmera, que gira com o olhar e não sai do lugar quando a câmera anda. Só vale em cenas 3D; numa cena 2D é recusado. As vistas ortográficas olham numa direção só e mostram a cor do horizonte do céu: as capturas de cima e de lado (`view` `top` e `side` do `oxy_screenshot`).
- `{"color": [r, g, b, a]}` é uma cor, de 0 a 1, como a imagem a mostra (a mesma conta do seletor de cor do editor e do código `#RRGGBB`). O fundo é opaco: `a` precisa ser 1, e uma cor fora de 0 a 1 é recusada.
- `"default"` volta ao fundo de uma cena nova do mesmo tipo: o céu numa cena 3D, a cor escura numa cena 2D.
- As cenas 3D novas (do `create_scene`, do `oxy_new_project` e do editor) começam com o céu, e as 2D com a cor escura. Uma cena feita antes de a cena ter fundo continua escura, e o arquivo dela não muda até alguém escolher um fundo; os exemplos e as receitas do guia continuam assim.

**Jogo exportado.** `set_game_settings {title?, window?, fullscreen?}` diz como o jogo exportado abre; o que não vier fica como está. É um comando do projeto, sem `scene`, e o editor o desfaz como os outros.
- `title` é o nome do jogo: o título da janela e o nome da pasta e do executável exportados (sem os caracteres que o Windows não aceita em nomes de arquivo). Tem até 80 caracteres, numa linha só; vazio, vale o nome do projeto, e renomear o projeto renomeia o jogo.
- `window` é `[largura, altura]` da área do jogo, de 320×240 a 7680×4320, na escala 100% do Windows (`[1280, 720]` por padrão). `fullscreen` (falso por padrão) abre o jogo em tela cheia; no jogo, Alt+Enter alterna entre a janela e a tela cheia.
- O progresso salvo não depende do título: fica na pasta do jogo pelo ID do projeto (veja **Progresso salvo**).

**Ações de entrada.**
- `create_input_action {name, key}` cria uma ação. O ID dela é o que os nós e o `oxy_simulate` usam (`"$N"` no mesmo lote).
- `rename_input_action {action, name}`, `set_input_key {action, key}` e `delete_input_action {action}` aceitam o ID ou o nome da ação. Um texto igual ao ID de uma ação vale por ela, antes dos nomes.
- A tecla é uma das de `input_keys` no catálogo: letras, números, as outras teclas do teclado, F1 a F35, Shift, os botões do mouse e a roda. Outras grafias que o jogo entende viram o nome do catálogo (`a` vira `A`, `ArrowUp` vira `Up`). Escape (abre o menu de pausa do jogo, numa cena que tem um, ou pausa o jogo e libera o mouse) e F3 (diagnóstico do player) são recusadas.
- `create_input_action` e `rename_input_action` recusam um nome que outra ação já tem ou que é o ID de outra ação (como `atacar` ou `pular` em projetos antigos), sem diferenciar maiúsculas.
- Os presets e componentes que criam as ações padrão (Pular, Correr, Agachar…) não fazem essa verificação. Se o nome de uma ação coincidir com o de outra, o lote avisa em `warnings`, e por esse nome os comandos e o `oxy_simulate` recusam a ação (ou, se ele for o ID de uma delas, escolhem essa); renomeie uma delas ou use o ID.
- Uma tecla que outra ação já usa é aceita, e o lote avisa em `warnings`, com as ações dessa tecla: no jogo, apertá-la dispara todas, e o `oxy_simulate`, que aperta ações e não teclas, não mostra isso. O `oxy_project` marca essas ações com `shares_key_with`.
- Nos nós, o parâmetro de ação de entrada (`ref` `input_action` no catálogo, como o `action` do `event.input` e do `input.read`) aceita o ID ou o nome da ação, com as mesmas regras do `rename_input_action`, e guarda o ID, que é o que o jogo lê. Antes, o nome era guardado como estava e o nó nunca disparava, com um aviso dizendo que a ação não existia. Um nome que duas ações têm é recusado; uma ação que o projeto não tem fica como foi escrita, com o aviso. Um nó que já guardava o nome de uma ação ganha um aviso próprio: `set_node_params` com o nome guarda o ID. Se o nome guardado for de mais de uma ação, o aviso lista os IDs delas, e o `set_node_params` precisa do ID da ação certa.
- Excluir uma ação em uso é recusado, com a lista de quem a usa.

**Superfícies físicas.**
- `create_surface` cria uma superfície a partir de um preset (`common`, `ice`, `mud` ou `conveyor`; `common` por padrão) e aplica os valores dados: `name`, `friction`, `traction`, `speed_multiplier`, `conveyor` (velocidade da esteira em m/s) e `conveyor_space` (`World` ou `Local`).
- `update_surface {surface, …}` muda só os valores dados. Valores negativos ou não finitos são recusados.
- `delete_surface {surface}` é recusado enquanto um colisor, personagem, atributo ou nó usa a superfície.
- Para aplicar uma superfície, use o `update_entity` em `physics3d.surface` ou `character3d.body.surface`.

**Variáveis do jogo.** Guardam valores do jogo inteiro, como uma contagem ou a cena em que o jogador parou, que a lógica lê e muda e que continuam iguais ao mudar ou reiniciar a cena. Cada partida começa com os valores iniciais: o teste do editor, o jogo aberto de novo e cada `oxy_simulate`. A exceção são as variáveis salvas entre partidas, que começam no progresso salvo, quando há (veja **Progresso salvo**, abaixo).
- `create_variable {name, value, persistent?}` cria uma variável e responde o ID dela (`"$N"` no mesmo lote). `value` é o valor inicial e dá o tipo da variável: `Number`, `Text`, `Bool`, `Vector2` ou `Vector3`. Um número, um texto ou `true`/`false` simples vale pela forma; um vetor leva o tipo (`{"Vector3": [0, 1, 0]}`). Objetos e superfícies são recusados: um objeto deixa de existir ao mudar de cena. `persistent` marca a variável para ser salva entre partidas (falso por padrão): o nó `save.write` a salva, e a partida seguinte começa no valor salvo.
- `update_variable {variable, name?, value?, persistent?}` muda o que vier. Um valor simples é lido no tipo atual da variável (num `Number`, `"dez"` é recusado com a forma esperada); para mudar o tipo, mande o valor com o tipo, como `{"Text": "Início"}`.
- `delete_variable {variable}` é recusado enquanto um nó usa a variável, com a lista desses nós.
- `variable` é o ID ou o nome. Os nomes não se repetem, sem diferenciar maiúsculas, e não têm `·`, que os relatórios usam para separar a chave (`Nome · chave`). O projeto tem até 256 variáveis, e um texto tem até 4096 bytes.
- Na lógica, `variable.get` (**Ler variável do jogo**) fornece o valor em `value`, e `variable.set` (**Alterar variável do jogo**) grava o `value`, que precisa ser do tipo da variável: outro tipo para o comportamento do objeto, com o erro no relatório. Os dois ficam na categoria **Jogo**. O parâmetro `variable` (`ref` `variable` no catálogo) aceita o ID ou o nome da variável e guarda o ID; uma variável que o projeto não tem é recusada, com a lista das variáveis.
- A chave (`key`, texto, no parâmetro ou na entrada de mesmo nome) guarda um valor por chave: ligue `scene.current.name -> variable.set.key` (e o mesmo no `variable.get`) para um valor por cena. Sem chave, vale o valor único da variável; uma chave em que nada foi gravado dá o valor inicial. Cada variável guarda até 1024 chaves durante a partida, e uma chave tem até 4096 bytes.

**Progresso salvo.** Os nós da categoria **Jogo** guardam as variáveis marcadas com `persistent` de uma partida para outra. Nada é salvo sem eles: mudar uma variável não basta.
- `save.write` (**Salvar progresso**) salva o valor atual de cada variável salva entre partidas, com todas as chaves. As outras variáveis ficam de fora.
- `save.clear` (**Apagar progresso**) apaga o progresso e volta as variáveis salvas entre partidas ao valor inicial, chaves incluídas.
- `save.state` (**Ler progresso salvo**) fornece `exists` (booleano): se há progresso salvo, de uma partida anterior ou desta. Serve, por exemplo, para mostrar um botão Continuar.
- O jogo exportado guarda o progresso em `%APPDATA%\OXY Engine\Jogos\<id do projeto>\progresso.json`, pelo ID do projeto, que não muda ao renomear o jogo. Um arquivo que não dá para ler é guardado à parte (`progresso.json.ilegivel-….json`) e o jogo começa sem progresso; um arquivo de uma versão mais nova do jogo nunca é gravado por cima. Os problemas aparecem só no diagnóstico do jogo (F3).
- O teste do editor guarda o progresso na memória, separado do jogo exportado: o próximo **Jogar** começa dele, e ele some ao abrir outro projeto ou com **Apagar progresso do teste**, em **Variáveis do jogo**. Cada gravação e cada apagamento viram uma linha no Console, como `Teste: progresso salvo — Recorde · Cena 2 = 41.2`.
- O `oxy_simulate` nunca lê nem grava esses progressos: o progresso entra pelo `save` e sai no relatório (veja abaixo).

**Pausa do jogo e sair.** O jogo pode se pausar sozinho, para mostrar um menu de pausa feito na lógica. Essa pausa é do jogo e fica separada da pausa da engine (o **Pausar** do teste do editor, a perda de foco): as duas podem acontecer juntas, e retomar a engine volta o jogo ao estado em que estava, pausado ou não.
- `game.pause` (**Pausar / retomar jogo**, categoria **Jogo**) pausa, retoma ou alterna a pausa, conforme `mode`: `pause`, `resume` ou `toggle` (o padrão). `game.read` (**Ler estado do jogo**) fornece `paused` (booleano).
- `event.pause` (**Ao pausar ou retomar**, categoria **Eventos**) dispara a cada mudança da pausa do jogo, qualquer que seja a causa, conforme `when`: `pause` ou `resume`. Uma cena com esse evento tem menu de pausa: a tecla Esc pausa e retoma o jogo, em vez de pausar a engine. Um menu típico é um grupo de interface oculto ao começar, que `event.pause(pause)` mostra e `event.pause(resume)` esconde com `action.component` (`visible`), com um botão Continuar (`event.click -> game.pause(resume)`). O fundo do menu pode ser um elemento `Image` sem imagem: ele desenha um retângulo na cor do elemento, com a transparência dela.
- Na pausa do jogo, o mundo para: movimento, animações, áreas, `event.step` e as esperas (`control.wait`), inclusive as iniciadas durante a pausa, que só terminam depois de retomar. A lógica, as ações de entrada e os cliques nos elementos da interface continuam; cliques em objetos do mundo são ignorados, e o mouse fica livre. As ações de entrada continuam disparando: para ignorá-las na pausa, a lógica lê `game.read`. O tempo do jogo (`time.read`, as esperas) para na pausa; os tempos do relatório do `oxy_simulate` seguem o relógio da simulação, que não para.
- Mudar de cena termina a pausa, sem disparar o `event.pause`: a cena nova começa sem pausa.
- `game.cursor` (**Mostrar / esconder cursor**, categoria **Jogo**) mostra ou esconde o cursor, conforme `mode`: `show` (o padrão) ou `hide`, sem pausar o jogo: o mundo, a lógica e as ações de entrada continuam. Com o cursor à mostra, o mouse fica livre e visível e os botões da interface recebem cliques, mas o mouse não gira a câmera: o `look` das entradas programadas não gira nada, e a saída `look` do `input.axes` vale (0, 0). `hide` devolve o mouse à câmera que gira com ele. Serve para uma tela de resultado ou um menu que deixa o jogo rodando; para parar o personagem, use `character.block` ou a pausa do jogo. Mudar de cena volta ao padrão, com o cursor escondido. `cursor_free`, no relatório do `oxy_simulate` e no `play` do `oxy_status`, diz se o cursor está livre.
- `camera.mode` (**Trocar modo da câmera**) com `mode` `fixed` (**Fixa na vista atual**) para a câmera onde a vista está: o objeto câmera passa para lá, e movê-lo depois (com `transform.write`) move a vista; movido no mesmo passo da troca, a vista vai até o novo ponto pela transição. Mover o objeto antes da troca não muda nada, pois a troca o põe de volta na vista. `fixed_object` (**Fixa no objeto câmera**) leva a vista à posição e à rotação do objeto câmera. Numa câmera que não é a ativa, ou que já está fixa, as duas usam o objeto câmera como ele está. Fixada na vista atual a partir da primeira pessoa, a câmera continua escondendo as peças escondidas em primeira pessoa (`hidden` do controle de câmera) até o objeto câmera ser movido. Em qualquer modo, a câmera atravessa o corpo do personagem que acompanha. A câmera fixa também solta o mouse; para soltá-lo sem mexer na câmera, use `game.cursor`.
- `game.quit` (**Sair do jogo**) encerra o jogo: o jogo exportado fecha a janela, o teste do editor para (como **Parar**) e o `oxy_simulate` termina, com `stopped_at` de `reason` `quit` e, em `object`, o objeto cuja lógica pediu para sair.

**Som.** Os nós de som ficam na categoria **Som**. Todos tocam WAVs importados, pelo ID do recurso no parâmetro `asset` (`ref` `audio` no catálogo).
- `action.sound` (**Reproduzir WAV**) toca o som uma vez, no canal de efeitos, com `volume` de 0 a 1.
- `action.sound_loop` (**Tocar em loop**) toca o som em loop, no canal `channel`: `music` (o padrão) ou `effects`. A música toca um som por vez: pedir o que já toca só muda o volume, e ele segue sem recomeçar, também depois de mudar ou reiniciar a cena; outro som entra no lugar, e os dois se cruzam em `fade` segundos (0 a 60; 0 = de uma vez). Nos efeitos, cada som tem o seu loop, até 32 (o 33º para o comportamento com erro), e os loops acabam com a cena. O volume (0 a 1) vem do parâmetro ou da entrada `volume`.
- `action.sound_stop` (**Parar som**) para os loops de `asset` no canal `channel` (`music`, `effects` ou `all`, o padrão), saindo em `fade` segundos. Com `asset` vazio (o editor mostra **Todos os sons do canal**), para todos os loops do canal. Os sons tocados uma vez acabam sozinhos.
- `action.volume` (**Volume do canal**) muda o volume de `channel`: `master` (geral, o padrão), `music` ou `effects`, de 0 a 1, pelo parâmetro ou pela entrada `volume`. Cada som é ouvido no volume geral vezes o do canal vezes o dele. Os volumes valem até o fim da partida, também depois de mudar de cena, e cada partida começa com todos em 1. Para o jogo lembrar a escolha, guarde-a numa variável salva entre partidas e aplique-a com `action.volume` ao começar. `audio.read` (**Ler volumes**) fornece `master`, `music` e `effects`.
- A pausa do jogo congela os efeitos, e a música continua; a pausa da engine congela tudo, e **Parar** silencia o teste.

Os comandos de ações de entrada, de superfícies, de variáveis, de recursos (`rename_asset` e `delete_asset`) e o `set_game_settings` valem para o projeto todo e, como os de cena, não recebem `scene`.

**Cenas pelo nome.** Todo campo de comando que recebe uma cena (`scene`, `to_scene`, o `scene` do `set_start_scene`, `rename_scene`, `duplicate_scene` e `delete_scene`) e o parâmetro `scene` dos nós `action.scene` e `value.scene` (`ref` `scene` no catálogo) aceitam o ID ou o nome da cena, sem diferenciar maiúsculas, e os nós guardam o ID, que é o que o jogo lê. Um nome que duas cenas têm é recusado; uma cena que o projeto não tem também, com o campo, o que ele recebeu e a lista das cenas: `Comando 7 (add_node, o 8º do lote): O parâmetro scene do nó action.scene recebeu "Menu 2", que não é o ID nem o nome de uma cena do projeto. Cenas: [{"id":"…","name":"Menu"}, …]`. Antes, só o ID valia, e o erro citava o ID interno do nó. A validação também deixou de citá-lo: uma referência quebrada diz o objeto, o nó pelo nome e o parâmetro e, numa cena, lista as cenas só pelo nome, porque a mensagem também aparece para você no editor (`Referência quebrada: objeto Portal, nó Mudar de cena (action.scene): o parâmetro scene recebeu "…". Cenas: Menu, Pista`).

**Colisores.**
- O `add_component` dá ao colisor de caixa (`collider3d`, `sensor3d`, `collider2d`, `sensor2d`) as dimensões da forma naquele momento. Depois, a caixa acompanha a escala do objeto, mas não as mudanças de dimensões: um `update_entity` em `dimensions` depois do `add_component` deixa a caixa com o tamanho antigo, e o jogador atravessa a parte nova. O lote avisa quando isso acontece, com o tamanho da forma e o da caixa. O aviso vale também para uma caixa que o `fit_collider` ajustou à forma do objeto, com ou sem `margin`; numa forma plana (um `Plane`, um `Rectangle`), a espessura da caixa não conta.
- `fit_collider {entity, children?, margin?, shape?}` ajusta o colisor à forma do objeto, como o **Ajustar ao objeto** do editor, ou, com `children: true`, à forma dele e de todas as peças dentro dele, como o **Ajustar ao grupo/filhos** (câmeras e elementos da interface ficam de fora). `margin` soma uma folga, em metros, em todos os lados (0 por padrão). Só a forma e o centro mudam: uma área continua área, e o filtro de colisão, a superfície e o liga/desliga ficam como estavam.
- `shape` escolhe a forma do colisor 3D: `box`, `sphere`, `capsule`, `convex`, `mesh` ou `auto`. Sem `shape`, o colisor é ajustado na forma que já tem (uma esfera continua esfera; um convexo é gerado de novo).
  - `box`: no 3D, a caixa continua girada com o objeto: o tamanho e o centro são medidos nos eixos dele, então um grupo girado e com escala envolve as peças sem sobra. No 2D, o colisor é sempre uma caixa e recebe a caixa das peças no mundo, como no editor (`shape` aceita só `box` e `auto`). Uma esfera, uma cápsula ou um convexo viram caixa.
  - `sphere`: centrada nas peças, com o raio do maior meio lado delas. `capsule`: de pé (eixo Y), com o raio do maior entre o meio lado em X e em Z e a altura das peças (no mínimo o diâmetro). As duas exigem escala uniforme no mundo; com outra escala, o comando é recusado e sugere `box` ou `convex`.
  - `convex` e `mesh`: o **Convexo da peça** e a **Malha estática da peça** do editor, gerados da forma do próprio objeto (o convexo fecha as aberturas; a malha as mantém). Não valem com `children` nem com `margin`.
  - `auto`: `box` para `Cube`, `Plane` e com `children`; `sphere` para uma `Sphere` redonda; `convex` para uma `Sphere` esticada pelas dimensões ou pela escala, que a esfera não acompanharia, e para `Cylinder`, `Cone` e `Pyramid`; `mesh` para `Tube` e malhas editáveis.
- Um colisor convexo ou de malha guarda a geometria de quando foi gerado. Um `update_entity` que muda a forma do objeto (as dimensões, a malha) deixa o colisor com a forma antiga, e o lote avisa, com o comando que gera de novo: `fit_collider {"entity": "…", "shape": "mesh"}`. Como no colisor de caixa, o aviso vem uma vez, no comando que deixou o colisor para trás; mudanças seguintes na forma não o repetem.
- São recusados, com o motivo: o Personagem 3D (a colisão dele é o corpo, em `character3d.body`), um objeto sem colisor e, sem `children`, um objeto sem forma própria, como um grupo. Antes, cápsulas, esferas e colisores convexos ou de malha também eram recusados.
- **Filtro de colisão pelo nome dos grupos.** No `update_entity`, `category` (os grupos em que o colisor está) e `mask` (os grupos que ele encontra) dos filtros de colisão, `physics3d.filter` e `character3d.body.filter`, aceitam, além do número (os bits), uma lista com os nomes dos grupos de colisão que o `oxy_project` lista em `collision_groups`, sem diferenciar maiúsculas, ou `"all"` para todos: `{"physics3d": {"filter": {"category": ["Áreas"], "mask": ["Personagens"]}}}` grava `category` 4 e `mask` 2. O projeto continua guardando os bits. Um nome que o projeto não tem é recusado com a lista dos grupos (`physics3d.filter.category: o grupo de colisão "Personagem" não existe; grupos: Cenário padrão, Personagens, Áreas…`). Os presets aceitam o mesmo em `filter` (veja **Presets e perfis de movimento**), e o `oxy_entity` mostra, ao lado dos bits, `category_groups` e `mask_groups`, os nomes dos grupos (`"all"` quando todos os bits estão ligados). Antes, só os bits valiam, e o agente convertia `1 << bit` à mão.
- Na lógica, o nó `action.component` com `component` `collider` (**Colisão / área (2D e 3D)**) liga e desliga o colisor do objeto: o colisor de caixa 2D, o colisor 3D sólido ou a área 3D (os dois, num objeto antigo que tem ambos). Antes, valia só para o colisor de caixa, e num colisor 3D o nó parava com erro. Desligado, o colisor sai das consultas da lógica já no mesmo passo, e quem estava em cima de um colisor sólido perde o apoio e cai.

**Reaproveitar entre fases.**
- `duplicate_entities {ids, offset?, count?}` faz `count` cópias (de 1 a 100; 1 por padrão). A cópia k fica a k × `offset` do original, em relação ao pai (`[0.5, 0, 0]` por padrão, como no editor), e as animações que movem o objeto vão junto. Uma fileira de plataformas a cada 4 m é um comando só: `{"op": "duplicate_entities", "ids": ["$0"], "offset": [4, 0, 0], "count": 10}` põe 10 cópias depois da original. Com mais de uma cópia, os nomes ganham o número: `Plataforma (cópia 3)`.
- `copy_entities {ids, to_scene, parent?}` copia objetos, com tudo o que está dentro deles, da cena `scene` (a do comando ou a da ferramenta) para `to_scene`, na raiz ou dentro de `parent`. Eles ficam no mesmo lugar do mundo, e as animações que os movem fazem o mesmo percurso no mundo: uma plataforma que anda 4 m continua andando 4 m dentro de um grupo com escala 2 ou girado. Se a escala não uniforme do pai de destino deformasse o objeto ou a animação, a cópia é recusada. Para outra cena, as referências precisam ficar dentro da cópia: um atributo, um vínculo da interface, uma câmera, um nó ou uma animação que aponta para um objeto que não vai junto faz o comando ser recusado, com a lista do que falta. Copie esses objetos junto.
- Os nós `action.scene` copiados continuam abrindo a cena que já abriam, e os `value.scene`, fornecendo a cena que já forneciam. Quando é a cena de onde a cópia saiu (um "reiniciar fase" levado para a fase 2 reabriria a fase 1), o lote avisa, com a lista desses nós; cada um vem com o nome e o ID da cópia que o tem (`Filho (<ID>) → nó action.scene (<nó>)`), inclusive as peças dentro dos objetos copiados, que não aparecem em `created`. Aponte-os para a cena nova com `set_node_params`, no mesmo lote pelo original (`"$N@<ID do objeto>"` e `"$N@<ID do nó>"`, veja **Cópias no mesmo lote**). Um nó com a entrada `scene` ligada não entra no aviso, mesmo que o parâmetro ainda nomeie a cena antiga: no jogo, quem decide é a entrada.
- `save_model {entity, name?, folder?}` guarda o objeto e tudo o que está dentro dele como um modelo, um recurso do projeto (o nome padrão é o do objeto), com a mesma regra das referências. Num projeto em pastas, o arquivo do modelo é `<folder>/<nome>.modelo.json` (na raiz, sem `folder`; uma pasta que falta é criada na hora, no mesmo passo), gravado quando o projeto é salvo; um arquivo com esse nome na pasta é recusado, com um nome livre sugerido. Um nome que outro modelo já tem é recusado, sem diferenciar maiúsculas, porque o `place_model` acha os modelos pelo nome; a recusa lembra o `replace`, para trocar o conteúdo desse modelo em vez de salvar outro. O **Salvar hierarquia como modelo** do editor também não repete nomes: se já houver um modelo `Torre`, o novo se chama `Torre 2`. `place_model {model, parent?, position?, name?}` coloca uma cópia do modelo na cena, pelo ID, pelo nome do modelo ou pelo caminho do arquivo dele (`Pista/Checkpoint.modelo.json`, com ou sem a extensão), com a raiz em `position` (em relação ao pai). As referências internas (lógica, câmera, animações) apontam para as peças colocadas. Um modelo que não existe é recusado com a lista dos modelos do projeto.
- A raiz colocada fica com o nome que tinha ao ser salva, que o `oxy_project` mostra em `root`, a menos que venha `name`; a resposta traz o nome de cada peça em `created`, a raiz primeiro. Duas colocações sem `name` ficam com o mesmo nome, e o `click` por nome e os rótulos passam a não distingui-las: dê um `name` a cada uma.
- `save_model {entity, replace, name?}` troca o conteúdo do modelo `replace` (o ID ou o nome dele) pelo objeto e o que está dentro dele, com a mesma regra das referências. O modelo mantém o ID, o arquivo (com `replace`, `folder` é recusado: para levar o modelo a outra pasta, use `move`) e, sem `name`, o nome; com `name`, é renomeado (um nome que outro modelo tem é recusado). As colocações já feitas são cópias editáveis, que só guardam de que modelo vieram: continuam com as peças que tinham, e só os `place_model` seguintes trazem o conteúdo novo. Para atualizar uma colocação, exclua a raiz dela e coloque o modelo de novo. No histórico do editor, o passo se chama **Agente: Substituir modelo**.
- `rename_asset {asset, name, kind?}` renomeia um recurso de qualquer tipo que o `oxy_project` lista (textura, áudio ou modelo), pelo ID, pelo nome (sem diferenciar maiúsculas) ou pelo caminho do arquivo. O ID não muda, e é ele que os nós e os objetos guardam. Num projeto antigo o arquivo na pasta `assets` fica como está; num projeto em pastas (`"layout": "Tree"`), o nome é o do arquivo, e renomear renomeia o arquivo na mesma pasta, na hora. Um script também se renomeia, pelo caminho e com `kind: "Script"`, e os objetos que o anexam acompanham. Um nome que outro recurso do mesmo tipo tem é recusado; recursos de tipos diferentes podem ter o mesmo nome, e então `kind` (`Texture`, `Audio` ou `Model`) diz qual deles: `{"op": "rename_asset", "asset": "Checkpoint", "kind": "Model", "name": "Ponto de controle"}`. Sem `kind`, um nome de dois recursos é recusado com a lista deles; com `kind`, um nome que só um recurso de outro tipo tem é recusado dizendo o tipo dele (`O recurso Placa é uma textura, não um modelo`). Dois recursos do mesmo tipo com o mesmo nome se distinguem pelo ID, que o `oxy_project` lista, ou, num projeto em pastas, pelo caminho; a recusa cita o arquivo de cada um, e não o ID, e num projeto em pastas pede `kind` ou o caminho: `"checkpoint" é o nome de 2 recursos: Checkpoint (modelo, Pista/Checkpoint.modelo.json), Checkpoint (áudio, Sons/Checkpoint.wav); passe kind (Model ou Audio) ou o caminho do arquivo`.
- `delete_asset {asset, kind?, detach?}` tira um recurso do projeto, como o **Excluir** da Biblioteca. É recusado enquanto algo o usa, com a lista dos usos (os mesmos do `used_by` do `oxy_project`): um objeto que mostra a imagem, um nó que toca o som, uma colocação do modelo, pela raiz. As colocações de um modelo saem com o `delete_entities` das raízes. Num projeto antigo o arquivo continua na pasta `assets`; num projeto em pastas ele vai na hora para a lixeira do projeto (`.oxy/lixeira`), e a resposta traz `trashed`. Ao vivo, o desfazer traz o recurso e o arquivo de volta. Um script se exclui pelo caminho, com `kind: "Script"`; anexado a objetos, é recusado, a menos que `detach: true` o tire deles. Um som ou modelo que um script cita pelo nome, como `audio.play("Checkpoint")`, não impede a exclusão, mas ela vem com um aviso que aponta a linha: `scripts/checkpoint.luau:19: audio.play: o som "Checkpoint" não existe mais no projeto; atualize o script, que no jogo para com erro nessa linha`.
- `create_folder {path}`, `rename_folder {folder, name}`, `move {items, to, kind?}` e `delete_folder {folder}` mexem nas pastas de um projeto em pastas (num projeto antigo, nos arquivos, o lote o organiza em pastas antes, e a resposta traz `converted`; ao vivo, são recusados até a pessoa salvar o projeto, o que o organiza). Os arquivos mudam no disco na hora e as referências acompanham (caminhos dos recursos e scripts anexados, nas cenas e nos modelos); a resposta traz `moved: [{from, to}]` e, quando pastas são criadas ou apagadas, `created_folders` e `removed_folders`. O `move` aceita caminhos de arquivos e pastas ou recursos pelo ID ou nome, para uma pasta (`""` é a raiz; uma pasta que falta é criada, com as de cima); um nome que já existe lá é recusado, com um nome livre sugerido, nunca por cima. O `delete_folder` sobe para a raiz o que a pasta tem (um nome que já existe lá ganha número, "Pulo 2"), manda `Thumbs.db` e `desktop.ini` para a lixeira e apaga a pasta; nenhum recurso é excluído. Se a gravação falhar, os arquivos voltam para onde estavam.
- Mover ou renomear scripts, ou as pastas deles (o `delete_folder` também, ao subir os itens para a raiz), reescreve os `require` escritos por inteiro que deixariam de achar o módulo: nos scripts que pedem o que mudou de lugar e nos próprios scripts movidos, cujos `./` e `../` passam a contar de outra pasta. O caminho novo é sempre `@project/Pasta/nome`, nas mesmas aspas (simples ou duplas; uma string longa `[[…]]` ou entre crases vira aspas duplas); um `require` que continua achando o módulo fica como está. A resposta traz `rewritten` com os scripts regravados, onde o lote os deixou (releia o texto deles antes de editá-los), e o desfazer volta os textos junto com os arquivos; ao vivo, o Console mostra `Agente · Script Pista/usa.luau alterado (require atualizados)` para cada um. Não são atualizados um `require` com caminho montado (`require("./" .. nome)`) nem um usado como valor (`pcall(require, "./dados")`, `local r = require`): os dois aparecem em `warnings` sempre que scripts mudam de lugar, com o arquivo e a linha, e a conferência do `check` e do `write` também avisa deles. Num script que declara um `require` seu (nome local, função ou parâmetro), as chamadas ficam como estão, e cada uma que precisaria do caminho novo vem em `warnings` com o caminho a escrever.
- Esses seis comandos, de recursos e de pastas, valem para o projeto todo e não recebem `scene`. No histórico do editor, são **Agente: Renomear recurso**, **Agente: Excluir recurso**, **Agente: Criar pasta**, **Agente: Renomear pasta**, **Agente: Mover para pasta** e **Agente: Excluir pasta**.
- Os nós `action.scene` e `value.scene` de um modelo continuam com a cena que tinham quando ele foi salvo, e o `place_model` não avisa: o modelo não guarda de que cena veio, e uma porta para a fase seguinte abre outra cena de propósito. Um "reiniciar fase" salvo na fase 1 e colocado na fase 2 reabre a fase 1; depois do `place_model`, aponte esses nós para a cena nova com `set_node_params` (os IDs estão em `created`, a raiz primeiro), ou monte o reinício pela entrada `scene`, como abaixo.
- **Reiniciar e seguir para outra cena sem ID fixo.** O `action.scene` tem a entrada `scene` (Texto). Ligada, ela decide a cena que o nó abre, no lugar do parâmetro `scene`, que fica como está (vazio, de preferência). O nó `scene.current` (**Cena atual**, categoria **Jogo**) fornece a cena em que o objeto está: `scene`, o ID, e `name`, o nome.
  - Reiniciar a cena: `event.input(reiniciar).exec -> action.scene.exec` e `scene.current.scene -> action.scene.scene`. A mesma lógica, levada com `copy_entities` ou salva num modelo e colocada com `place_model`, reinicia a cena em que estiver, sem aviso e sem `set_node_params`. No `oxy_simulate`, a troca vem com `reload: true`.
  - Seguir para a próxima cena: o nó `value.scene` (**Referência de cena**, categoria **Dados**) fornece em `value` o ID da cena escolhida no parâmetro `scene`. Ligue `value.scene.value -> action.scene.scene`, ou guarde o ID num atributo de texto do objeto e ligue `attribute.get.value -> action.scene.scene`, com `attribute` no nome do atributo. O atributo recebe o ID pelo `set_attribute` (`{"Text": "<ID da cena>"}`) ou, na lógica, por `value.scene.value -> attribute.set.value`. Cada cena tem a sua cópia do objeto, com a cena seguinte.
  - O `value.scene` também fornece em `name` (**Nome**) o nome da cena escolhida, como o `scene.current`. Num menu, ligue `value.scene.name -> variable.get.key` para ler o recorde de cada fase guardado por nome, sem escrever o nome à mão: renomear a fase muda o nome que o nó fornece, assim como o que a fase grava pelo `scene.current.name`.
  - A entrada espera o ID da cena, não o nome. Um texto vazio, um nome ou um ID que o projeto não tem para o comportamento do objeto, e o relatório traz o erro com o objeto e o nó: `Cena de destino não existe: a entrada Cena recebeu "Fase 2", o nome de uma cena; a entrada espera o identificador…`. Sem a entrada ligada, o parâmetro vale como antes, e um parâmetro vazio continua sendo erro.
  - Com a entrada ligada, o parâmetro é ignorado e não segura a cena que nomeia: `delete_scene` (e o **Excluir cena** do editor) não recusa a exclusão por causa desse nó e deixa o parâmetro vazio.
  - O editor não mostra IDs de cena. Quem monta pelo editor escolhe a cena pelo nome: no parâmetro de cada cópia do `action.scene` ou numa **Referência de cena**, que leva o ID à entrada `scene` ou a um atributo de texto. O `value.scene` segura a cena que nomeia como o `action.scene`: o `delete_scene` recusa a exclusão, e o aviso do `copy_entities` o lista. Vazio, ele para o comportamento que o lê, com erro.
- O jogador dos presets tem a câmera ao lado, e não dentro dele. Para levar o jogador com a câmera para outra fase, agrupe os dois (`create_entity` de um grupo e `set_parent`) e salve o grupo como modelo. A interface e a lógica de um cronômetro vão do mesmo jeito: num grupo, com os objetos que elas usam.

**Plataformas móveis e animações.**
- O preset `platform` aceita `travel` (quanto a plataforma anda a partir de onde é posta, em metros; `[4, 0, 0]` por padrão) e `period` (segundos da ida e da volta, com as paradas; 4 por padrão). Ele cria uma animação comum, em loop, que um nó toca quando a cena começa.
  - `pause_at_ends` são os segundos que a plataforma fica parada em cada ponta (0 por padrão), dentro do período: menos que metade dele. Ela sai andando quando a cena começa, para na ponta de lá, volta e para onde foi posta; os quadros-chave das pontas seguram a pose (`hold`). Com `"travel": [0, 0, -8], "period": 9, "pause_at_ends": 1.5`, a plataforma leva 3 s em cada sentido e espera 1,5 s em cada ponta, o que dá tempo de embarcar.
  - `spin` são os graus que a plataforma gira em X, Y e Z por período, enquanto anda (nada por padrão), levando junto e girando quem está em cima: `[0, 360, 0]` dá uma volta em Y a cada período; nas paradas, o giro também para. Com `travel` `[0, 0, 0]`, a plataforma só gira, e a animação se chama **Giro** (com os dois, **Translação de ida e volta com giro**). Cada ida e cada volta ganham um quadro-chave a cada 90° no máximo, somando os eixos, porque entre dois quadros-chave o giro vai pelo caminho mais curto. Para recomeçar sem salto, a animação dura os períodos que o giro leva para voltar ao começo, com voltas inteiras em todos os eixos: 1 com 360° por período, 2 com 180°, 4 com 90°, 8 com 45°. Um giro que precisaria de mais de 8 períodos, ou que passa de 3600° por período somando os eixos, é recusado, assim como uma parada de metade do período ou mais. As duas opções valem só para o preset `platform`.
- `set_transform` move junto os quadros-chave do objeto quando as animações dele mesmo o movem, como as de uma plataforma móvel. Assim, a plataforma movida continua indo e voltando a partir do lugar novo; na 0.5.0, o jogo a devolvia ao percurso antigo. Um giro gira o percurso em volta do lugar do objeto, e os ângulos de cada quadro-chave mudam o mesmo tanto que os do objeto (um quadro-chave a 120° num objeto girado 30° passa a 150°, e um a 360°, a 390°). Uma escala muda a escala dos quadros-chave, sem mudar o percurso. `move_tracks: false` deixa os quadros-chave como estão; `move_tracks: true` também move as trilhas que outras animações têm para o objeto (a peça de um boneco, por exemplo). O editor segue a mesma regra ao mover, girar ou escalar o objeto pelas alças ou pelas Propriedades, fora da aba Animação.
- `set_clip {entity, clip?, name, duration, looping?, tracks, events?}` cria uma animação do objeto ou substitui a animação `clip` (pelo ID ou pelo nome), mantendo o ID que os nós usam. Cada trilha anima o próprio objeto (`target` ausente ou `"self"`) ou uma peça dentro dele, com quadros-chave `{time, position?, rotation?, scale?, interpolation?}`: transformações locais, com a rotação em graus e `interpolation` `linear` (padrão) ou `hold` (fica parado até o próximo). O que o quadro-chave não diz vem da transformação atual do alvo, e o pivô dele é mantido. `events` são marcadores `{time, name}`, que o nó `event.animation` usa pelo nome. Para tocar a animação, use o nó `action.animation` com o ID dela em `clip`.
- `delete_clip {entity, clip}` exclui uma animação; é recusado enquanto um nó `action.animation` a toca, com a lista desses nós.
- Na lógica, o `action.component` com `component` `platform` (**Plataforma móvel**) liga e desliga a plataforma móvel do objeto. Uma plataforma por velocidade para e volta a andar de onde parou; ao voltar, leva quem está em cima no mesmo passo em que anda, sem lançá-lo. Uma plataforma que segue a animação só deixa de levar quem está em cima, e a animação continua: para parar o movimento, desligue também a animação (`component` `animation`).
- Na lógica, o nó `transform.write` (**Mover / girar / escalar objeto**, categoria **Transformação 3D**) muda a posição (`channel` `position`, em metros), a rotação (`rotation`, em graus XYZ) ou a escala (`scale`) de qualquer objeto, ao executar. `mode` `set` define o valor; `add` soma (na escala, multiplica). `space` `local` usa os eixos do pai, como as Propriedades e o `set_transform`; `world`, os do mundo, com a posição do pivô, como `world.position` do `oxy_entity` e o `transform.read` em `world`. Somar à rotação em `local` soma aos ângulos, que voltam por voltas inteiras depois de uma volta completa; em `world`, gira o objeto nos eixos do mundo. A escala só muda em `local` e não chega a zero; a rotação em `world` é recusada quando a escala não uniforme de um grupo acima deformaria o objeto. A escala negativa (espelho) do próprio objeto não muda os ângulos.
  - O nó recusa a raiz de um personagem 3D (use `character.teleport` e `character.yaw`) e um objeto que uma animação em reprodução move (pause-a com `action.component`, `component` `animation`), com o nome do objeto e da animação no erro.
  - Uma plataforma que segue a animação, movida ou girada assim a cada passo, leva quem está em cima. `jump: true` faz do movimento um salto: a plataforma solta quem está em cima, sem lançá-lo, como num movimento maior que o `max_transport_per_step` dela.
- Uma plataforma móvel que gira, pela animação ou pela lógica, leva quem está em cima em volta do eixo dela e o gira junto. Em primeira pessoa a câmera gira junto; em terceira pessoa, não. Quem pula herda a velocidade do ponto da plataforma sob os pés, conforme `inherit_platform` do personagem. As outras peças da plataforma (o que está dentro dela, como um parapeito) não barram quem ela leva. Um giro de mais de 20° num passo de 1/60 s (1200° por segundo), uma mudança de escala ou um salto soltam quem está em cima, sem lançá-lo, com um aviso. Um corpo em caixa que, ao girar, entraria numa parede deixa de girar naquele passo, mas continua sendo levado. Para uma volta inteira numa animação, ponha um quadro-chave a cada 90° no máximo: entre dois quadros-chave, o giro vai pelo caminho mais curto (quadros-chave a 0° e 360° dão a mesma pose, e a plataforma não gira).
- Uma animação posiciona as peças enquanto toca e no passo em que termina (sem loop). Terminada ou pausada, deixa as peças onde a lógica as puser; na 0.5.0, uma animação terminada repunha a pose final a cada passo.

**Interface do jogo.**
- Um elemento da interface é o `ui` de um objeto: o `create_entity` com `{type: ui, element}` cria um (`Text`, `Image`, `Button` ou `Bar`), e o `update_entity` edita os campos dele, que o `ui_elements` do catálogo lista em `fields`: a âncora, o deslocamento e o tamanho em pixels da vista do jogo, o texto, a cor, a imagem, o vínculo e o máximo de uma barra.
- `text_align` põe cada linha de um texto (`Text`) à esquerda (`Left`, o padrão), no centro (`Center`) ou à direita (`Right`) do retângulo do elemento, como o **Alinhamento** do editor. Botões e barras mantêm o texto no centro.
- `text_size` é o tamanho da letra de um texto ou do rótulo de um botão, em pixels da vista do jogo, de 10 a 96, como o **Tamanho do texto** do editor em px; fora disso, o lote é recusado (`Tamanho do texto de Título deve ficar entre 10 e 96 px; recebeu 120`). Sem ele (`null` no patch), o tamanho é automático, como antes: metade da altura do elemento, de 12 a 32 px, num texto, e 16 px num botão (15 px num botão com imagem). As barras usam sempre o tamanho automático delas. Por exemplo, um título grande no centro: `{"op": "update_entity", "entity": "…", "patch": {"ui": {"text_align": "Center", "text_size": 48}}}`.
- Com o padrão (à esquerda e automático), os dois campos ficam fora do arquivo do projeto, que continua igual ao de antes; o `oxy_entity` os mostra no `ui` só quando mudam. O relatório do `oxy_simulate` e o `ui` do `oxy_screenshot` trazem o tamanho com que cada texto é desenhado e o alinhamento de cada texto.

**Presets e perfis de movimento.**
- Os presets de personagem (`first_person` e `third_person`) aceitam `camera`: `create` (padrão) cria a Câmera principal; `reuse` faz a câmera ativa da cena (ou a primeira) seguir o novo jogador, sem criar outra; `none` não põe câmera nenhuma. `reuse` é recusado se a cena não tem câmera ou se a câmera já segue outro objeto. Sem a Câmera principal, as peças seguintes sobem uma posição na resposta.
- Os três presets aceitam `filter: {category?, mask?}`, o filtro de colisão do corpo do personagem ou do colisor da plataforma, com os bits ou os nomes dos grupos, como no `update_entity` (veja **Colisores**): `{"type": "preset", "preset": "first_person", "filter": {"category": ["Personagens"]}}` põe o jogador no grupo Personagens. O que ficar de fora mantém o padrão (`category` Cenário padrão, `mask` todos).
- `apply_movement_profile {entity, profile}` aplica um perfil de movimento (`direct`, `parkour` ou `chained`) a um personagem 3D, como o botão do editor: os valores listados no catálogo são escritos no personagem e continuam editáveis.

**Mudanças em relação à 0.5.0:**
- O `oxy_apply` responde `{created, warnings}` em vez de `{applied: [{op, created}]}`.
- Os marcadores também valem dentro do `patch`. Um texto que é inteiro `"$N"` passou a ser marcador também no primeiro comando do lote, onde é recusado; para o texto em si, use `"$$N"`.
- Um preset devolve todas as peças, não só a raiz.
- `add_node` e `set_node_params` recusam valores fora das opções e números fora da faixa do parâmetro.
- `set_transform` move junto os quadros-chave dos objetos que as próprias animações movem, como as plataformas móveis (`move_tracks: false` mantém o comportamento antigo). O editor faz o mesmo.
- O preset `platform` aceita `pause_at_ends` (paradas nas pontas) e `spin` (giro por período); antes, uma plataforma que para ou gira pedia um `set_clip` com os quadros-chave à mão.
- `duplicate_entities` sem `count` nem `offset` continua fazendo uma cópia a 0,5 m em X.
- As mensagens de erro contam os comandos do 0, como `"$N"` e `created`, e dizem a posição por extenso (`Comando 1 (set_node_params, o 2º do lote)`); antes, contavam do 1.
- Os parâmetros de ação de entrada dos nós guardam o ID também quando recebem o nome, e os parâmetros aceitam valores simples quando o catálogo dá o tipo ou, nos parâmetros de qualquer tipo, pela forma do valor.
- `save_model` recusa o nome de outro modelo; `fit_collider` é novo e, com `shape`, faz esferas, cápsulas e o convexo ou a malha da peça.
- Os nós sem `position` ganham lugar organizado no fim do lote, em vez de uma fileira só, e há o `arrange_logic`.
- O `connect` aceita `links` com várias ligações, e o `add_node`, `links` com as entradas do nó novo (veja **Ligar a lógica em menos comandos**). Os erros de ligação citam os nós pelo nome.
- `"$N@<ID>"` e `"$N.M@<ID>"` chegam às cópias no mesmo lote; um texto assim passou a ser marcador (para o texto em si, `"$$N@<ID>"`).
- O `save_model` aceita `replace`, que troca o conteúdo de um modelo mantendo o ID; há o `rename_asset` e o `delete_asset`, para recursos de qualquer tipo; e o `oxy_project` mostra a raiz de cada modelo e, com `model`, as peças dele.
- O `arrange_logic` aceita `split_shared_data` e avisa dos fios longos que ficaram; o `disconnect` aceita `links`, como o `connect`.
- Há o `set_game_settings`, que diz como o jogo exportado abre (título, janela e tela cheia), e o `oxy_project` traz isso em `game`.
- Há o `set_scene_background`, que dá a uma cena o Céu da OXY ou uma cor de fundo; as cenas 3D novas começam com o céu, e o `oxy_project` e o `oxy_scene` trazem o fundo em `background` (veja **Fundo da cena**).
- Há variáveis do jogo (`create_variable`, `update_variable` e `delete_variable`), os nós `variable.get` e `variable.set` e os de progresso salvo, `save.write`, `save.clear` e `save.state`.
- O `action.scene` ganhou a entrada `scene` e há os nós `scene.current`, na categoria nova **Jogo**, e `value.scene` (**Referência de cena**, com as saídas `value`, o ID, e `name`, o nome), em **Dados**. Não há migração: a entrada não é salva no nó, só a conexão. O aviso de nós copiados que ainda abrem ou nomeiam a cena de onde vieram deixa de fora os que têm essa entrada ligada e sugere ligá-la, e esses nós também não impedem o `delete_scene`.
- Há a pausa do jogo e o sair: os nós `game.pause`, `game.read` e `game.quit`, em **Jogo**, e o evento `event.pause`, em **Eventos** (veja **Pausa do jogo e sair**). Há também o `game.cursor`, que solta o mouse sem pausar. O `time.read` e as esperas passaram a contar o tempo do jogo, que para na pausa do jogo; sem pausa, ele é igual ao de antes.
- Há música, loops e volumes: os nós `action.sound_loop`, `action.sound_stop`, `action.volume` e `audio.read`, na categoria nova **Som**, para onde o `action.sound` foi, sem mudar os parâmetros (veja **Som**).
- Há o nó `transform.write` (**Mover / girar / escalar objeto**), e uma animação terminada ou pausada deixa de repor a pose a cada passo (veja **Plataformas móveis e animações**).
- O `ui` de um elemento da interface ganhou `text_align` e `text_size` (veja **Interface do jogo**).
- Uma plataforma móvel que gira leva quem está em cima e o gira junto, com a câmera em primeira pessoa; na 0.5.0, qualquer giro soltava o apoio com aviso. Agora só um giro de mais de 20° num passo solta, e o aviso diz que a plataforma `girou rápido demais`.
- O `camera.mode` `fixed` mantém a vista atual e põe o objeto câmera nela; na 0.5.0, a vista ia para onde o objeto câmera estava, o que agora faz o `fixed_object`. Escrever a transformação do objeto câmera antes da troca deixou de ter efeito: mova-o depois. A câmera fixa passou a atravessar o corpo do personagem que acompanha, como nos outros modos, e, fixada na vista atual a partir da primeira pessoa, continua escondendo as peças escondidas em primeira pessoa até o objeto ser movido.
- O `transform.read` em `world` dá a posição do pivô, como as Propriedades e o `oxy_entity`; antes, dava a origem do objeto, que difere do pivô num objeto com pivô. Num personagem 3D, continua dando a origem, onde o `character.teleport` o põe.
- O `character.teleport` descarta só os eventos do trajeto abandonado que ainda não executaram: as aterrissagens, os contatos e as entradas e saídas de áreas que o personagem fez no mesmo passo, e o `event.step` e o `event.input` da lógica dele naquele passo. A lógica que já começou continua, esperas (`control.wait`) incluídas, seja de que objeto for. Antes, o teleporte cancelava também as esperas dos fluxos que o personagem tinha iniciado: um gatilho com `event.area_enter → control.wait → esconder o ladrilho → control.wait → mostrar o ladrilho` nunca mostrava o ladrilho de volta se quem pisou caísse e fosse teleportado no meio da espera.
- O catálogo do `event.input` diz que ele dispara em todo objeto que tem o nó, inclusive num personagem com `automatic_input` desligado: nesta versão a entrada é uma só para o jogo inteiro.

**Scripts.** `attach_script {entity, path, index?}` anexa ao objeto um script do projeto, pelo caminho a partir da pasta do projeto (`Pista/porta.luau`), na posição `index` da lista dele (no fim, sem `index`), e cria no objeto, no mesmo passo de desfazer, os atributos que o script declara em `Modulo.attributes` e que ele não tem, com o valor padrão. A resposta diz quais criou, em `attributes_created`, pelo índice do comando: `{"attributes_created": {"0": ["Ordem"]}}`. Um evento do script que nunca rodaria naquele objeto, como o lote o deixa, vem nos avisos: `on_area_enter` e `on_area_exit` num objeto sem área (`Controle da corrida não tem área (sensor3d): on_area_enter de scripts/checkpoint.luau nunca roda nele; adicione o componente sensor3d (add_component) ou anexe o script à área`; numa cena 2D, o aviso pede `sensor2d`) e `on_click` num objeto que não recebe cliques; um `add_component` da área mais adiante no lote resolve, e não há aviso. Veja [Scripts com o agente](#scripts-com-o-agente). `detach_script {entity, path}` tira o script e mantém os atributos. `set_script_enabled {entity, path, enabled}` liga ou desliga um script anexado (o **Ligado** do cartão Scripts no editor).

**Tirar a lógica de nós.** `clear_logic {entity}` tira do objeto o grafo inteiro, todos os nós e ligações, num comando só, e mantém os scripts, os atributos e os componentes; num objeto sem nós, o lote passa com o aviso `Porta não tinha lógica de nós; nada mudou nele`. Não é um dos comandos de nós, que são legado e continuam como estão (`remove_node` tira um nó por vez, pelo ID). É o comando da troca de nós por script: veja a receita em [Scripts com o agente](#converter-um-objeto-de-nós-para-script). Antes, tirar o grafo pedia um `remove_node` por nó, ou um `update_entity` com `{"graph": {"nodes": [], "edges": []}}`.

**Nomes que os scripts citam.** Renomear ou excluir um som, um modelo, uma cena, uma ação de entrada, uma superfície ou uma variável do jogo que um script cita com um texto literal (`audio.play("Bipe")`, `scene.change("Fase 2")`, `vars.get("Moedas")`, `input.pressed("Pular")`) é feito, e o lote avisa com o arquivo, a linha e o nome novo, porque no jogo a chamada pararia com erro: `Comando 0 (rename_asset, o 1º do lote): scripts/porta.luau:3: audio.play: o som "Bipe" agora se chama Apito; atualize o script, que no jogo para com erro nessa linha`. O aviso vem no comando que renomeou, moveu ou excluiu o que o nome achava, mesmo num lote com outros comandos do mesmo tipo. Ele também vem do `delete_folder`, que pode numerar o nome de um arquivo que sobe para a raiz, e do `move` e do `rename_folder` de um modelo que um script põe pelo arquivo: o `scene.spawn_model` acha o modelo pelo nome e, quando o texto não é o nome de um modelo, pelo caminho do arquivo (`scene.spawn_model("Pista/Torre.modelo.json")`, sem diferenciar maiúsculas), e o aviso diz o arquivo novo (`o modelo "Pista/Torre.modelo.json" agora está em Modelos/Torre.modelo.json`). No editor, renomear ou excluir uma variável do jogo, renomear ou excluir uma cena, excluir uma ação de entrada ou uma superfície e renomear ou excluir na Biblioteca um som ou um modelo (ou mover um modelo) que um script cita dá o mesmo aviso no Console, também em **Avisos**. Só conta o texto escrito por inteiro onde é usado, como na conferência de nomes; um nome montado na hora não é visto. Renomear de volta no mesmo lote, ou mudar só as maiúsculas de um nome que o jogo acha em qualquer caixa, não avisa.

## Scripts com o agente

Na 0.7, a lógica pode ser escrita em Luau, em arquivos `.luau` de qualquer pasta do projeto, com nomes livres (`Pista/Checkpoint.luau`, `Comum/sons.luau`, `scripts/porta.luau`). Um script é conhecido pelo caminho a partir da pasta do projeto, com `/`, na caixa que o disco tem. Pastas e arquivos que começam com ponto (`.oxy`, `.vscode`, `.git`, `.solucoes`) ficam fora do projeto, como as subpastas que são outro projeto ou um jogo exportado, e os atalhos (links e junções) não são seguidos. O grafo de nós continua funcionando, mas não ganha nós novos. Um objeto roda os scripts que anexa, na ordem da lista, depois da lógica de nós dele.

Um script usa outro com `require`, pelo caminho do arquivo sem `.luau`: `require("@project/Pista/dados")` a partir da pasta do projeto (a forma que continua certa quando o script muda de pasta), ou `require("./dados")` e `require("../Comum/sons")` a partir da pasta do próprio script. Os dois caminhos levam ao mesmo módulo, que roda uma vez e é o mesmo para todos. O caminho nunca sai da pasta do projeto; `@self`, os apelidos do `.luaurc` (o jogo exportado não lê nenhum), `.luau` no fim e um nome com outras maiúsculas são recusados, com o que escrever (`require("./DADOS"): Pista/DADOS.luau não existe; quis dizer ./dados?`).

- **O disco é a verdade.** O script é o arquivo, e não existe script "não salvo", nem no editor. O agente grava pelo `oxy_scripts` ou, se tiver ferramentas de arquivo, direto no arquivo; o efeito é o mesmo.
- **`oxy_scripts`**, pelo `action`:
  - `list`: todos os scripts do projeto, `{total, scripts}`, cada um `{path, lines, kind, used_by, requires?, required_by?, error?}`. `kind` é `script` (um objeto o anexa), `module` (um script que um objeto roda o pede com `require`, escrito por inteiro) ou `unused` (o jogo nunca o roda; a exportação o leva do mesmo jeito, se compilar); `requires` e `required_by` são os scripts que ele pede e os que o pedem, e `error`, por que ele não carrega.
  - `read {path}`: o texto, cada linha depois do número dela e de uma tabulação (que não fazem parte do arquivo), e `lines`.
  - `write {path, text}`: o arquivo inteiro, tudo ou nada. Antes de gravar, o texto é conferido como o jogo carrega o script: a sintaxe, um local do topo alterado dentro de uma função (o valor se perderia ao recarregar; o erro aponta a linha da mudança, ou a da função que usa o local quando quem o muda é o próprio topo) e o topo do módulo rodado sem mexer no mundo, com os outros scripts do projeto para o `require`. Com erro, nada é gravado, e a mensagem traz o arquivo e a linha: `Pista/porta.luau:3: erro de sintaxe: …; nada foi gravado`. As pastas são criadas, e um caminho com outras maiúsculas é o arquivo que o disco tem (a resposta traz o caminho certo). A resposta traz `saved`, `created`, `lines`, `added` e `removed` (as linhas novas e as que saíram) e os avisos.
  - `check {path?, text?}`: confere um script, um texto como se fosse aquele script (sem gravar) ou, sem `path`, todos os do projeto, e responde `{ok, checked, errors, warnings}`, cada diagnóstico como `Pista/x.luau:LINHA: mensagem`. Sem `path`, um `.luau` que não pode ser script (maior que 1 MB, que não é texto UTF-8, preso em outro programa) é um erro só dele, e os outros são conferidos; um `.LUAU` em maiúsculas e um `.luaurc` (ou `.config.luau`) de subpasta que muda o apelido `project` vêm nos avisos. Os avisos apontam funções com nome de evento que não existe (`on_aera_enter`, que nunca roda) e um `Modulo.attributes` que não é uma tabela de valores padrão, como o jogo avisa onde o script está anexado; um módulo que outros scripts usam com `require` e que nenhum objeto anexa pode ter funções `on_*` e um `attributes` só dele, sem aviso. Os tipos não são conferidos aqui (`types_unavailable`): quem os confere é o VS Code com a extensão luau-lsp.
  - **Conferência de nomes** (no `check` e no `write`): os nomes do projeto que o script escreve como texto literal são conferidos contra o projeto, pelas regras com que o jogo os procura, e um nome que o projeto não tem vem nos avisos com a linha e o nome mais parecido (ou a lista, quando nenhum é parecido): `scripts/porta.luau:5: audio.play: o som "Checkpointt" não existe no projeto; quis dizer Checkpoint?`. Valem os sons (`audio.play`, `audio.loop`), as variáveis do jogo (`vars.get`, `vars.set`), os atributos (`obj.attr.Vida`, `obj.attr["Ponto de retorno"]`, `has_attribute`, `scene.with_attribute`: um atributo que nenhum objeto do projeto tem e que nenhum script declara em `Modulo.attributes`), as cenas (`scene.change`), os modelos (`scene.spawn_model`), as ações de entrada (`input.pressed`, `held`, `released`), os clipes (`obj.animation:play`), os objetos (`scene.find`, `scene.get`, `scene.find_all`, `obj:find_child`, `obj:get_child`) e as superfícies (`param.surface`, e o nome escrito em `obj.collider.surface` e `obj.character.body_surface`). No `on_input` e no `on_marker`, o texto com que a função compara o parâmetro (`if action == "Pular"`) também é conferido, e com o nome exato, porque a comparação diferencia maiúsculas: `action == "pular"` nunca é verdade, e o aviso diz `quis dizer Pular?`. Um texto fora das opções de um parâmetro (`camera.set_mode(cam, "orbita")`, `phase == "presed"`) e um nome da API que os scripts não têm (`audio.paly`, `math.flor`, `prnt`) também são avisados, e um `require` com caminho montado (`require("@project/Cartas/" .. nome)`, ou com `{}` entre crases) também, porque a OXY só atualiza os caminhos escritos por inteiro quando move ou renomeia arquivos. Cada nome vem uma vez, na primeira linha, com as outras linhas em que aparece. Só conta o texto escrito onde é usado (uma constante local do módulo também): um nome montado na hora, escolhido por um `if` ou passado numa tabela de opções (`audio.stop({ sound = "Musica" })`) não é conferido, e no jogo continua sendo recusado com o mais parecido. São avisos: o `write` grava do mesmo jeito.
  - `rename {path, to}`: renomeia ou move o script (outro nome, outra pasta ou os dois, como `Menu/porta.luau`; uma pasta que falta é criada). `delete {path, detach?}`: manda o script para a lixeira do projeto (`.oxy/lixeira`); anexado a objetos, é recusado com a lista deles, a menos que `detach: true` o tire deles antes. Os dois passam pelos comandos do `oxy_apply` (`rename_asset`, `move` e `delete_asset` com `kind: "Script"`): os objetos que anexam o script acompanham, os `require` escritos por inteiro são reescritos (`rewritten`), ao vivo é um passo do histórico que o Ctrl+Z desfaz com os arquivos, e a resposta é a do `oxy_apply`, com `path` (o caminho novo) ou `deleted`, como o disco escreve os nomes. Com outro nome e outra pasta, o script é renomeado onde o nome novo está livre, antes ou depois de mudar de pasta; quando o nome novo já existe na pasta de origem e o antigo na de destino, o pedido é recusado com os dois arquivos. Num projeto antigo, nos arquivos, o projeto é organizado em pastas antes.
  - `check` sem `path` traz também `unused`, os scripts que nenhum objeto roda.
  - `vscode`: grava o que o VS Code precisa (veja abaixo).
- **O Ctrl+Z não desfaz.** Ao vivo, o resto do que o agente faz se desfaz com Ctrl+Z e quem salva é você; a gravação de um script é a exceção: vai para o disco na hora, e o Ctrl+Z da OXY não a desfaz. Para voltar atrás, a primeira mudança de cada arquivo numa sessão guarda o arquivo como estava em `.oxy/agente/<caminho>.bak` (`.oxy/agente/Pista/porta.luau.bak`, `previous_version` na resposta), fora dos scripts do projeto: nos arquivos, uma vez por sessão do servidor; ao vivo, uma vez por sessão do editor. Se a cópia for apagada, a gravação seguinte a guarda de novo. Um arquivo que a sessão criou não tem cópia. A carga, o teste e a exportação leem só os arquivos `.luau` do projeto: outro arquivo fica de fora, e a exportação nunca leva as cópias.
- **Ao vivo**, o editor grava o arquivo, e o Console mostra `Agente · Script Pista/porta.luau alterado (+12 -3 linhas)` (ou `criado`). A gravação não espera você terminar um gesto nem parar o teste: é para isso que serve a recarga. Um projeto que nunca foi salvo não tem pasta para os scripts, e o editor recusa.
- **Recarga no teste do editor.** Durante um teste com scripts, e só durante ele, o editor olha os arquivos `.luau` de todas as pastas do projeto a cada 300 ms e lê de novo um arquivo que mudou e ficou parado por duas olhadas (os editores de texto gravam num arquivo temporário e o renomeiam). O texto novo entra entre dois passos, mesmo com o teste pausado, e o jogo continua de onde estava: atributos, memória dos scripts (`self.state`), variáveis e temporizadores ficam como estavam. O Console diz `Script recarregado: Pista/porta.luau (3 objetos)`. Um texto com erro, ou um arquivo que não pode ser lido, fica de fora, com o arquivo e a linha, e o teste segue com a versão anterior: `Script não recarregado: Pista/porta.luau:12: … O teste segue com a versão anterior.`, também em **Avisos**. Um atributo que o script passou a declarar não é criado durante o teste, porque o projeto não muda no teste: o Console avisa, e anexar o script de novo depois do teste cria o que falta. Os erros dos scripts durante o teste aparecem no Console com o arquivo e a linha, e o `oxy_console` traz também `script: {path, line}`.
- **Anexar e ler:** o `attach_script` do `oxy_apply` (com o objeto pelo ID ou pelo nome, como o `detach_script` e os outros comandos) só anexa um arquivo que o projeto tem (um caminho errado traz o mais parecido: `quis dizer Pista/porta.luau?`): escreva-o antes com o `oxy_scripts write`. Um caminho com outras maiúsculas anexa o arquivo na caixa que o disco tem, com um aviso (`o script pista/porta.luau está no disco como Pista/porta.luau, e foi anexado assim`). Um atributo declarado que o objeto já tem com outro tipo fica como está e vem nos avisos, como a conferência de nomes do script, uma vez por script, no último `attach_script` dele no lote e com o projeto como o lote o deixou (uma variável criada depois no mesmo lote conta). A resposta traz `attributes_created`, os atributos que cada `attach_script` criou, e avisa de um evento que nunca rodaria no objeto (`on_area_enter` sem área, `on_click` sem clique). O `oxy_scene` mostra os scripts de cada objeto, o `oxy_project` os objetos que rodam cada script, e o `oxy_entity` lista os scripts do objeto em `scripts`, com `missing: true` num arquivo que o projeto não tem e, nos outros, os eventos que o script define, os atributos e a memória que declara, o erro quando ele não carrega e os eventos que nunca rodam naquele objeto. O `oxy_validate` avisa dos scripts anexados que sumiram e traz a conferência de nomes de todos os scripts do projeto.
- **Ligar e desligar:** cada script anexado tem o seu liga/desliga naquele objeto, o **Ligado** do cartão Scripts das Propriedades. Desligado, o objeto continua com o script na lista, na mesma posição, mas o jogo (o teste do editor, o `oxy_simulate` e o jogo exportado) roda o objeto sem ele; um script desligado em todos os objetos nem é carregado. O `set_script_enabled {entity, path, enabled}` do `oxy_apply` liga e desliga, com desfazer (`Ligar script` e `Desligar script`), e o `oxy_entity` mostra `enabled: false` no script desligado (o ligado, o padrão, não traz o campo, e o arquivo do projeto também só grava `"enabled": false`). Desligar é uma escolha do projeto, salva com ele: não é o comportamento desligado por um erro do grafo, que afeta só o grafo, nem o script parado num objeto por estourar o limite de trabalho durante a partida.
- **Testar:** o `oxy_simulate` roda os scripts do projeto, como o teste do editor; os logs e os erros saem com o arquivo e a linha, o `script_time` do relatório diz quanto cada arquivo custou, o `script_errors` lista cada erro uma vez por objeto e linha, com quantas vezes aconteceu, e `check_vm_reset: true` confere que nenhum script guarda estado na VM (veja o **Relatório** em [Testes com `oxy_simulate`](#testes-com-oxy_simulate)).
- **VS Code.** O editor de scripts da 0.7 é o VS Code com a extensão **luau-lsp**, conferida na versão 1.70.1 (a sintaxe do arquivo de tipos muda entre versões, e uma mais nova pode não lê-lo): ela completa os nomes da API, mostra a ajuda em português e acusa nomes e tipos errados, como `audio.paly`. O `oxy_scripts vscode`, a primeira gravação de um script num projeto e o primeiro `attach_script` num projeto sem os tipos desta versão gravam sem perguntar (a resposta traz `vscode`, e ao vivo o Console diz o que foi gravado):
  - `.oxy/tipos/oxy.d.luau`: os tipos da API dos scripts, gravados de novo quando a versão da engine muda (não edite);
  - `.luaurc` com o apelido `"project": "./"`, para a extensão achar os `require("@project/…")` como o jogo acha (o jogo não precisa dele). Num `.luaurc` seu, a OXY junta só o apelido e deixa o resto como está; um que dá ao apelido outro valor, ou que tem comentários, fica como está, e as `notes` dizem o que mudar. Falta do apelido também conta para a gravação automática. Um `.luaurc` ou `.config.luau` de subpasta que redefine `project` vem nas `notes`, porque a extensão leria os `require` daquela pasta a partir dele;
  - no `.vscode/settings.json`, só as chaves `luau-lsp.*` que faltam: a plataforma `standard`, sem sourcemap, `fflags.sync: false` (com `true`, a extensão baixa as flags do Roblox e aceita o que a engine recusa), a definição `@oxy` e os 10 globais que os scripts não têm, como `os` e `math.random`. Uma chave que o arquivo já tem fica como está, e a resposta diz em `notes` o que mudar à mão; um arquivo com comentários não é tocado, e as chaves vão para `.oxy/vscode-settings.json`, para você copiar.

  Abra no VS Code a pasta do projeto, não só o arquivo do script, para a extensão ler esses arquivos.
- **A API.** O `oxy_catalog` lista a API: sem opções, os nomes de cada área; com `api` (os nomes ou prefixos, como `audio.` e `obj:`) ou `area`, a assinatura e a ajuda em inglês de cada função, o que os textos dela nomeiam no projeto e os nós que ela substitui (veja [Leituras compactas](#leituras-compactas)). A referência de cada função, com a assinatura, os parâmetros, o que faz a chamada parar com erro e um exemplo que roda num teste da engine, está em [API dos scripts](api-scripts.md). Ela é gerada da mesma tabela da engine que instala a API no jogo e escreve os tipos do VS Code, então nada que um script alcança fica fora dela. Os nomes da API são em inglês; os de objetos, atributos, sons, ações e variáveis são os que você deu. Uma propriedade com o nome errado diz o nome certo: `positon não é uma propriedade de Object; quis dizer 'position'? Para um valor do próprio script, use self.state ou um atributo`; um nome que não lembra nenhuma vira `self não aceita campos soltos (x); use self.state ou um atributo`.
- **Temporizadores.** `self:after(segundos, Modulo.f, ...)` chama `Modulo.f(self, ...)` depois desse tempo de jogo, no mínimo no passo seguinte, como o nó **Esperar sem bloquear** (`control.wait`): os dois, começados no mesmo passo com o mesmo tempo, disparam no mesmo passo. `self:sequence(intervalo, Modulo.f, itens)` chama `Modulo.f(self, itens[k])` aos `(k-1) × intervalo` segundos da chamada, como `self:after` chamaria cada item: o primeiro no passo seguinte, como `self:after(0)`, e os outros na grade das esperas de um grafo. `self:schedule({ {atraso, Modulo.f, dado?}, … })` conta cada atraso do passo anterior. Nenhum deles chama a função na hora: para portar um grafo que muda algo já no começo, antes de qualquer espera, faça a mudança direto no `on_start`. Uma contagem `3, 2, 1, Já!` que mostra o 3 ao começar e espera 1 s antes de cada um dos outros fica `Race.show(self, 3)` seguido de `self:sequence(1, Race.show, { 3, 2, 1, 0 })` (o primeiro item repete o 3 no passo seguinte), passo a passo igual ao grafo. Repetir o primeiro item só serve quando a função só grava estado (atributos, variáveis, memória), que gravado de novo não muda nada; se ela também toca um som, cria um objeto ou manda uma mensagem, o efeito sai duas vezes. Nesse caso, grave só o estado no `on_start`, ou chame `Race.show(self, 3)` e depois `self:schedule({ {1, Race.show, 2}, {1, Race.show, 1}, {1, Race.show, 0} })`, que dá os mesmos passos sem repetir. É o que faz a contagem do parkour, que toca um bipe em cada número (`Pista/controle_da_corrida.luau`).
- **Variáveis do jogo.** `vars.get(nome, chave?)` acha a variável pelo nome, sem diferenciar maiúsculas; numa chave que nunca foi gravada, dá o valor inicial da variável, como o nó **Ler variável do jogo**, e nunca `nil`. Um nome que o projeto não tem é um erro, no `vars.get` e no `vars.set`, com o nome mais parecido: `A variável do jogo "contagen" não existe no projeto; quis dizer Contagem? Variáveis: …`. As variáveis guardam o valor quando a cena reinicia (um botão Reiniciar ou um `action.scene` para a própria cena), no grafo e nos scripts: zere no `on_start` o que precisa recomeçar; senão, o que outro objeto lê no primeiro passo é o valor da partida anterior.
- **Atributos.** Ler um atributo que o objeto não tem dá `nil`; escrever é um erro que diz como criá-lo: `o atributo Avisoo não existe neste objeto (quis dizer Aviso?); declare-o em Modulo.attributes (anexar o script de novo cria o que falta) ou crie-o no objeto` (o agente cria com o `set_attribute` do `oxy_apply`). Quando uma chamada para num erro com `nil` (`tentou comparar um valor nil < um número`), o erro diz o último atributo que ela leu como `nil` e a linha: `(a linha 9 leu Jogador.attr.Ordem, que Jogador não tem: …)`. Os tipos sem valor literal se declaram com marcadores: `Modulo.attributes = { Alvo = param.object(), Piso = param.surface("Gelo"), Tamanho = param.vector2(1, 1) }` cria um atributo Objeto vazio (o objeto se escolhe nas Propriedades ou com o `set_attribute`, e a escolha sobrevive a renomear o objeto), um Superfície com a superfície do projeto de nome `Gelo` (sem nome, a padrão; um nome que o projeto não tem é avisado e nada é criado) e um Vetor2; no script, o Objeto lê o objeto ou `nil`, o Superfície, a superfície (com `.name`) ou `nil`, e o Vetor2, um vetor com z = 0. Em `Modulo.state`, os mesmos marcadores declaram campos que começam vazios (`alvo = param.object()`, `piso = param.surface()`, sem nome) e um Vetor2; um campo de objeto ou de superfície recebe `nil` para ficar vazio.
- **Objetos e cena.** `obj.parent`, `obj:children()`, `obj:find_child(nome)` (`nil` se não houver) e `obj:get_child(nome)` (erro que lista os filhos) andam na Hierarquia; `scene.find`, `scene.get`, `scene.find_all` e `scene.with_attribute` acham objetos pelo nome exato ou por um atributo, na ordem da cena. `obj.visible` mostra e esconde (o painel da contagem do parkour some com `self.attr.Painel.visible = false`, sem grafo); `obj.logic_enabled` liga e desliga só o grafo do objeto. `obj:clone(opções)` e `scene.spawn_model(nome, opções)` criam cópias com IDs que se repetem a cada partida igual, e o `on_start` delas roda depois da chamada; `obj:destroy()` remove na hora (`self:destroy()` encerra a chamada em silêncio no próximo uso de `self`). `scene.change(nome)` e `scene.restart()` valem quando a função termina. Uma propriedade com o nome errado, em outra caixa ou como outra engine a chama (`self.hidden`, `self.Visible`) diz a certa: `hidden não é uma propriedade de Object; quis dizer 'visible'? (…)`.
- **Transformação e contas.** `obj.rotation` (graus, como as Propriedades), `obj.orientation` (quatérnio), `obj.scale`, `obj.yaw` (só leitura), `obj:jump_to(p)` e `obj:to_world_direction(v)` passam pelas regras do nó **Mover / girar / escalar objeto**. `vmath` soma ao `vector` do Luau o `normalize_or_zero`, o `flat`, o `distance`, o `lerp` e o `yaw_of`; `quat` faz os giros (`from_euler`, `look_at`, `slerp`, `multiply`, `rotate`…). Um quatérnio nunca muda e não vai para a memória, temporizadores nem mensagens: guarde `quat.to_euler(q)`.
- **Personagem, física, animação e interface.** As partes de um objeto chegam por propriedades: `obj.character`, `obj.collider`, `obj.platform`, `obj.controller`, `obj.animation` e `obj.ui`. Ler uma delas num objeto que não tem a peça é um erro que diz o nome do objeto (`Caixa não tem Personagem 3D (confira antes com obj:has_component("character"))`). O `obj.character` lê o estado de **Ler personagem 3D** (`position`, `velocity`, `grounded`, `posture`, `support`, `surface`, a do chão em que ele pisa…), a superfície do corpo (`body_surface`, que também se escreve), a mira (`aim`, uma direção de comprimento 1 que vem da entrada simulada, não da imagem da câmera, e dá o mesmo em toda máquina) e o olhar (`look`, em graus: x o giro, y a inclinação). Os comandos são os dos nós: `move`, `jump`, `set_posture`, `add_velocity`, `set_velocity`, `block`, `apply_profile` (`"agile"` é o perfil Ágil com embalo), `set_param`, `get_param`, `set_option`, `set_yaw` e `teleport(pés, { search, keep_velocity, yaw, look })`. Um teleporte sem espaço não é erro: devolve `false` e o motivo; com espaço, `true`, `nil` e onde os pés ficaram. `obj.collider.enabled`, `obj.platform.enabled` e `obj.controller.enabled` ligam e desligam as peças, como **Ativar / desativar componente**; `obj.animation:play("Abrir")` toca um clipe pelo nome; `obj.ui.text` e `obj.ui.color` (vermelho, verde e azul de 0 a 1 num vetor) mudam um elemento de interface sem atributo vinculado. `physics.raycast`, `sphere_cast`, `capsule_cast` e `capsule_fits` consultam a cena sem mover nada: sem contato dão `nil`, e uma consulta recusada dá `nil` e o motivo. Um nome errado de parâmetro, opção, postura, modo ou clipe é recusado com o mais parecido e a lista.
- **Câmera, som, jogo e entrada.** `camera.active()`, `camera.look()`, `camera.forward()` e `camera.mode()` leem a câmera de jogo, e `camera.activate`, `set_mode`, `follow`, `look_at`, `release_look` e `set` recebem o objeto câmera. `audio.loop`, `audio.stop`, `audio.set_volume` e `audio.volume` fazem o que os nós de som em laço e de volume fazem. `game.pause`, `resume`, `paused`, `show_cursor`, `hide_cursor` e `quit`, e `save.write`, `clear` e `exists`, são os do jogo e do progresso salvo. `input.pressed`, `held` e `released` acham a ação pelo nome de **Lógica > Ações de entrada**; duas ações com o mesmo nome são um erro que pede para renomear uma delas. `input.movement()`, `input.look()` e `input.wheel()` dão os eixos do passo. Um segundo argumento `player` só chega na 0.8, com vários jogadores. `time.now()`, `time.dt` e `time.format(segundos, "mm:ss")` contam o tempo de jogo; `random.number`, `random.integer`, `random.seed` e `random.stream("ondas")` sorteiam pela engine, com uma sequência para cada objeto e script, e dão o mesmo numa repetição. `players`, `Player`, `session`, `game.online`, `game.is_host`, `game.is_server`, `on_request`, `on_player_join` e `on_player_leave` ficam reservados: usar um deles é um erro que diz que ele chega na 0.8.
- **Tipos pelo script.** Com `type Self = ScriptObject<typeof(M.attributes), typeof(M.state)>` e `self: Self` nas funções, o luau-lsp acusa no VS Code um atributo ou um campo da memória que o script não declara (`self.attr.Avisoo = "x"`), um valor de outro tipo e um atributo Objeto usado sem conferir o `nil`. Com `self: Object`, os atributos e a memória aceitam qualquer nome, e só o jogo acusa.
- **Som de quem joga.** O `audience` de `audio.play` é aceito, mas só passa a escolher quem ouve na 0.8, com vários jogadores; até lá, o único jogador ouve todo som. Para tocar só para o jogador, confira um atributo do personagem, como o `Jogador local` do parkour, como no exemplo abaixo.

A área de checkpoint do parkour (`Pista/checkpoint.luau`), por exemplo, com o som só para o jogador:

```lua
--!strict
-- Área de checkpoint: um arquivo para os 6 checkpoints da pista e o modelo Checkpoint. Quem
-- passa por um checkpoint mais adiante guarda a Ordem dele e volta ali, nos pés, ao cair.
local Checkpoint = {}
Checkpoint.attributes = { Ordem = 1 }
local PES = vector.create(0, 1.5, 0) -- do centro da área até o chão

function Checkpoint.on_area_enter(self: Object, other: Object)
    if not other:has_attribute("Checkpoint atual") then
        return -- uma caixa de física também entra na área
    end
    local ordem = self.attr.Ordem
    if other.attr["Checkpoint atual"] < ordem then
        other.attr["Ponto de retorno"] = self.world_position - PES
        other.attr["Checkpoint atual"] = ordem
        if other.attr["Jogador local"] then
            audio.play("Checkpoint", { volume = 0.9, audience = other })
        end
    end
end

return Checkpoint
```

### Converter um objeto de nós para script

A lógica de nós continua rodando, então converter é uma escolha, objeto por objeto, e o comportamento tem de ficar igual. A receita, só pelo MCP:

1. **Ler a lógica.** `oxy_entity {id: "Checkpoint 1"}` resume o grafo: os eventos, os nós pelos rótulos (`event.area_enter`, `attribute.set(Checkpoint atual)`, `action.sound(Checkpoint)`) e as ligações. Com `graph: "full"` vêm todos os parâmetros.
2. **Achar as funções.** `oxy_catalog {api: [...]}` dá a assinatura e a ajuda do que vai usar; o `nodes` de cada linha diz quais nós ela substitui, e o contrário também serve: o evento `event.area_enter` vira `on_area_enter`, o `action.sound` vira `audio.play`, o `control.wait` vira `self:after` (veja **Temporizadores**, acima, para uma espera que começa na hora). Os valores que o grafo lia de atributos ficam nos atributos, declarados em `Modulo.attributes`.
3. **Guardar o antes.** Rode o `oxy_simulate` que exercita a lógica (entradas, `bot`, `spawn` no lugar certo), com `watch` nos objetos e `actions: "all"`, e guarde o que importa: `sounds`, `logs`, `scene_changes`, `variables` e os atributos observados. O `state_hash` não serve para comparar, porque o grafo faz parte do estado.
4. **Escrever o script.** `oxy_scripts write`, que confere o texto e recusa com o arquivo e a linha; os avisos da conferência de nomes apontam um som ou um atributo escrito errado.
5. **Trocar, num lote só.** `[{"op": "attach_script", "entity": "Checkpoint 1", "path": "Pista/checkpoint.luau"}, {"op": "clear_logic", "entity": "Checkpoint 1"}]`. A resposta traz `attributes_created` e avisa de um evento que nunca rodaria no objeto. Ao vivo, é um passo que o Ctrl+Z desfaz (o arquivo do script fica, como toda gravação de script).
6. **Comparar.** O mesmo `oxy_simulate`, agora com `check_replay: true` e `check_vm_reset: true`: os mesmos sons, logs, trocas de cena e valores nos mesmos tempos, `script_errors` ausente e `replay` e `vm_reset` com `identical: true`.
7. **Os outros objetos.** Um script serve a todos os objetos com a mesma lógica (os valores de cada um ficam nos atributos, como a `Ordem` de cada checkpoint): repita o passo 5 para eles, num lote, e o 6 uma vez no fim.

## Testes com `oxy_simulate`

O teste roda numa cópia do projeto, na memória. Nada é salvo, e nada muda no editor nem no histórico.

- **Entradas programadas** (`inputs`): ações de entrada com horário. Continuam valendo depois de uma troca de cena ou de reiniciar a cena, e uma tecla segurada continua segurada.
  - `press` e `release` usam o ID ou o nome de uma ação de entrada do projeto (ou `"$N"` de uma ação criada no `setup`). Uma ação que o projeto não tem é recusada, com a lista das ações; na 0.5.0, ela era apertada em vão.
  - `movement` é a intenção de andar, `[direita, frente]` de -1 a 1, e vale até o próximo `movement`.
  - `look` é um movimento do mouse, aplicado uma vez: cada unidade gira a câmera pela sensibilidade dela (no controle de câmera, 0,12° por padrão). `x` positivo vira para a direita e `y` positivo olha para baixo, a menos que a câmera inverta o eixo. Na pausa do jogo e com o cursor à mostra (nó `game.cursor`), não gira nada.
  - `click` clica num objeto ou botão da interface, como uma pessoa, pelo ID, pelo nome (sem diferenciar maiúsculas, quando nenhum outro objeto do projeto tem esse nome) ou por `"$N"` do `setup`. O objeto pode ser de qualquer cena, para clicar num botão de uma cena que o jogo abre depois. Um ID ou nome que nenhum objeto tem é recusado antes de rodar (`click: "Jogar" não é o ID nem o nome de um objeto do projeto`); na 0.5, o clique era ignorado em silêncio. Os IDs das cópias que o `action.spawn` faz durante o jogo são aceitos. Um elemento oculto (ele mesmo ou um grupo acima dele) não recebe o clique, e uma linha do log diz `Clique ignorado: Continuar está oculto…`; um objeto que não está na cena que roda naquele momento também não, com a linha `Clique ignorado: Continuar não está na cena atual (Menu).`. Na pausa do jogo, só os elementos da interface recebem cliques.
  - `click` com `point: [x, y]`, em vez de `entity`, clica num ponto da vista do jogo, em pixels a partir do canto de cima à esquerda, na vista de `width` × `height` (por padrão, a janela do jogo; veja **Tamanho da vista**), a mesma dos retângulos do `ui`. Como no jogo, o clique vai para o botão visível mais de cima naquele ponto (a camada maior; na mesma camada, o que vem depois na cena). Imagens e textos não recebem cliques, então um botão sob um painel continua clicável, como no jogo. Um ponto sem botão visível só escreve no log: `Clique ignorado: nenhum botão visível da interface em (750, 120).` O ponto vale só para a interface; objetos do mundo se clicam por `entity`. É assim que o agente confere o que o clique de uma pessoa em (560, 490) acionaria quando dois botões se sobrepõem. O `oxy_play` recusa o clique por ponto, porque a vista do jogo no editor tem o tamanho do painel.
  - `escape` faz o que a tecla Esc faz no jogo: numa cena com menu de pausa (um nó `event.pause`), pausa ou retoma o jogo; sem ele, uma linha do log diz que a cena não tem menu de pausa.
- **Cena inicial** (`scene`): a cena em que o teste começa, pelo ID ou pelo nome; sem ela, a cena inicial do projeto.
- **Tamanho da vista** (`width` e `height`): a vista do jogo em que o `ui` é medido, os cliques por `point` acertam os botões e o `screenshot` é desenhado, de 16 a 4096 pixels de lado. Sem eles, é a janela com que o jogo exportado abre (o `game.window` do `oxy_project`, que o `set_game_settings` muda, também no `setup`; 1280×720 sem ele), para que os retângulos e os pontos sejam os do jogo; uma janela maior que 4096 de lado é reduzida na mesma proporção. Um lado só fica com o outro da janela. O relatório diz o tamanho usado em `view_size`. Antes, o padrão era 960×540, e um ponto tirado de uma captura de 1280×720 errava o botão.
- **Preparar o teste** (`setup` e `spawn`):
  - `setup` aplica comandos do `oxy_apply` só na cópia, por exemplo um objeto de teste ou outro valor de atributo. Os comandos sem cena usam a cena em que o teste começa: a de `scene` ou, sem ela, a cena inicial do projeto. Ao vivo também é assim; o `oxy_apply`, ao contrário, usa a cena aberta no editor.
  - Para começar uma variável do jogo em outro valor (testar com 1 vida em vez de 3, por exemplo), use `update_variable` no `setup`: o teste sempre começa com os valores iniciais da cópia (as salvas entre partidas começam no `save`, quando ele vem).
  - `save` é o progresso que um jogador que volta ao jogo tem: `{variável: valor}`, com cada variável salva entre partidas pelo ID ou pelo nome (vale `"$N"` do `setup`), `Nome · chave` para o valor de uma chave e o valor simples ou com o tipo, como em `{"Recorde · Cena 2": 41.2, "Moedas": {"Number": 3}}`. Sem `save`, o jogo roda como recém-instalado. Uma variável que o projeto não tem, ou que não é salva entre partidas, é recusada; para testar uma variável comum com outro valor, use `update_variable` no `setup`.
  - `spawn` coloca um objeto, como o jogador, numa posição do mundo (e virado para um lado) antes de começar.
  - Os IDs criados no `setup` valem como `"$0"`, `"$1"`… (`"$0.1"` para o segundo ID do comando 0) no resto do pedido, e o relatório os lista em `setup`.
- **Parar quando algo acontecer** (`until`): troca de cena (`scene_change`: `true` para qualquer uma, reinícios incluídos, ou uma cena pelo ID ou pelo nome), um texto no log, um atributo que chega a um valor, uma variável do jogo que chega a um valor (`variable: {variable, key?, op, value}`, com o ID ou o nome da variável e, para comparar o valor de uma chave, `key`), um objeto que some, um evento (pulo, aterrissagem, entrada numa área…), a pausa do jogo (`paused: true` para quando ela começa, `false` para quando termina; o `ui` do fim mostra então o menu), um som que começa a tocar, uma vez ou em loop (`sound`, com o ID ou o nome do som; um loop que já tocava e só muda de volume não conta) ou o fim do bot (`bot`, veja abaixo). `seconds` vira o limite, e `stopped_at` diz o que parou o teste (`reason`) e quando, com o que aconteceu em palavras em `detail`, como `Jogador aterrissou em Pouso`; quando é um evento, `kind` traz o tipo dele (`land`, `jump`…), como em `events`. O valor comparado precisa ser do tipo do atributo ou da variável; num atributo de objeto ou de superfície, o texto é o ID (vale `"$0"`). Um `game.quit` encerra o teste mesmo sem `until`, com `reason` `quit`, `object` (`{id, name}`, o objeto cuja lógica pediu para sair) e o `detail` dizendo quem foi, como `Sair pediu para sair do jogo (nó Sair do jogo)`. Antes, o `detail` era sempre `O jogo pediu para sair (Sair do jogo)`, e o rótulo do nó podia ser confundido com um botão de mesmo nome.
  - `then_seconds` não é uma condição: quando uma condição acontece, o teste continua mais esses segundos antes de terminar, mesmo passando de `seconds` (o teste inteiro vai até 600 s). Assim, os sons, as gravações do progresso, as variáveis, a interface, o estado final dos objetos observados e a imagem (`screenshot`, e o `oxy_screenshot`) mostram o que veio depois, como a tela de resultado já assentada, numa corrida só. O `stopped_at.time` continua dizendo quando a condição aconteceu, e `stopped_at.ended_at`, quando o teste terminou. Um `game.quit` nesse tempo termina o teste antes, e o `detail` ganha o que aconteceu: `Jogador.Etapa == 3 (valor 3); depois, Sair pediu para sair do jogo (nó Sair do jogo)`. As `samples` se espalham pelo teste inteiro, o tempo depois da condição incluído. Se nenhuma condição acontece, o teste dura `seconds`, como sem `then_seconds`. Antes, ver a tela assentada pedia outra simulação, sem `until`, com `seconds` adivinhado.
- **Bot** (`bot`): leva um personagem 3D por um caminho de pontos, como uma pessoa nos controles. A cada passo, o bot dá ao movimento a direção do ponto seguinte e aperta as ações de entrada do próprio personagem (pular, correr, agachar), e a lógica do jogo as recebe como as de uma pessoa.
  - `{entity, path, radius?, start?, stuck_after?}`: `entity` é o personagem, de qualquer cena do projeto, pelo ID, pelo nome ou por `"$N"` do `setup`. São recusados um objeto que nenhuma cena tem, um personagem de cena 2D, um objeto sem Personagem 3D e um personagem com a entrada automática desligada (`automatic_input: false`), que ignora as entradas.
  - O bot espera a cena do personagem rodar: num jogo que começa no menu, ele assume depois que o menu abre a fase, e o tempo no menu não conta como sem avanço. `start` conta a partir do começo dessa cena (o `time` dela em `scene_changes`; 0 para a cena inicial), com a mesma regra do `at` das entradas: com `"start": 0.5`, o bot assume meio segundo depois que a fase começa. Se a cena do personagem começar de novo (ou o jogo sair dela e voltar) antes de o bot assumir, a conta recomeça do último começo. Assim, `Menu → Jogar → fim da fase` cabe numa simulação: `click` no botão Jogar e o bot no Jogador da fase. Antes, o bot só aceitava um personagem da cena inicial.
  - Depois que o bot assume, cada novo começo da cena do personagem (uma recarga, como a de um botão Reiniciar ou Jogar de novo, ou o jogo voltando a ela) recomeça o caminho do primeiro ponto, com o `start` contado desse começo: uma segunda corrida cabe na mesma simulação. Os campos do `bot` no relatório (`started_at`, `reached`, `done_at`, `stuck`, `held_by`) são da corrida mais recente, e `earlier` lista as anteriores, da mais antiga para a mais nova, com os mesmos campos; uma corrida que a recarga interrompeu não tem `done_at` nem `stuck`. O `until: {"bot": …}` para no primeiro fim, de qualquer corrida. Antes, depois de uma recarga o bot continuava mirando o ponto em que estava, a partir da largada.
  - Cada ponto de `path` é `[x, y, z]` no mundo, com `y` na altura dos pés (o topo do chão), ou `{at?, object?, jump?, sprint?, crouch?, wait?, radius?, wait_for?}`. Com `object` (pelo ID, pelo nome ou por `"$N"`, como o `object` do `wait_for`), o ponto segue um objeto da cena do personagem enquanto ele se move, como uma plataforma móvel: é a posição dele no mundo (o pivô) mais `at`, nos eixos do mundo. `jump` aperta o pulo uma vez ao sair do ponto: ponha o ponto onde o personagem toma impulso. Se o personagem chega ao ponto correndo de lado em relação ao ponto seguinte (mais de 1 m/s atravessado no caminho), o bot primeiro vira para o ponto seguinte no chão, por até 0,25 s, e só então pula, para o pulo sair naquela direção e não levar o embalo da chegada. Numa curva fechada logo antes de um pulo, um ponto antes do pulo, alinhado com ele, ainda dá um impulso mais limpo. `sprint` e `crouch` seguram correr e agachar a caminho do ponto e enquanto o bot espera nele (num agachar que alterna, o bot aperta uma vez por ponto para mudar). `wait` são os segundos parado no ponto, e `radius` muda o alcance só nesse ponto.
  - `wait_for: {object, within?, height?, timeout?}` faz o bot esperar parado, antes de ir para o ponto, até `object` (um objeto da cena do personagem) ficar ao alcance de onde ele está: o ponto anterior, depois da espera dele e antes do pulo (ou os pés do personagem, antes do primeiro ponto), na posição em que esse ponto está no momento. Ao alcance quer dizer que o topo do objeto (o do colisor 3D dele; sem colisor, o da forma e das peças dentro dele) fica a até `within` metros desse ponto no chão (1 por padrão; 0 quando o ponto está sobre ele) e a até `height` metros acima ou abaixo dele (por padrão, a altura de degrau do personagem, 0,25 m). Quando o ponto anterior segue um objeto, como uma plataforma em que o bot vai em cima, a medida é entre o topo desse objeto e o topo de `object`: a distância no chão entre os dois (0 quando se encostam) e a diferença de altura entre eles. Se o objeto não chega ao alcance em `timeout` segundos do tempo do jogo (30 por padrão), o bot desiste com `reason` `waiting`; se ele sai da cena que roda, o bot desiste com `absent` depois de `stuck_after` segundos, como num ponto que segue um objeto que sumiu. É o jeito de embarcar numa plataforma móvel sem uma espera calculada para a hora em que o bot chega:
    - para embarcar, um ponto que segue a plataforma e espera por ela: `{"object": "<Balsa>", "at": [0, 0.2, 0], "wait_for": {"object": "<Balsa>"}}` (com o ponto anterior na beira do cais);
    - para descer, um ponto no destino que espera pelo destino, com o bot parado sobre a plataforma enquanto isso: `{"at": [0, 0.5, -158], "wait_for": {"object": "<Cais de lá>"}}`. Como o ponto anterior segue a plataforma, o destino fica ao alcance quando o topo da plataforma chega a 1 m do topo dele, seja qual for o tamanho da plataforma; numa plataforma que encosta devagar, um `within` menor (como 0,2) faz o bot sair só com ela encostada. Num elevador, o mesmo: o ponto que segue o elevador espera por ele embaixo, e o ponto no andar de cima espera pelo andar de cima, que fica ao alcance quando o elevador chega lá.
    - Antes, embarcar pedia um `wait` calculado a partir de uma corrida anterior, que deixava de servir quando qualquer trecho antes da plataforma mudava de tempo.
  - O ponto conta como alcançado quando o personagem fica a até `radius` dele no chão (0,6 m por padrão) e a até meia altura do corpo na vertical.
  - Enquanto conduz, o bot substitui as entradas de movimento: as `movement` e as ações de direção do personagem deixam de valer. As outras entradas continuam. Nesta versão o jogo tem uma entrada só: o movimento do bot vale para todo personagem da cena com entrada automática, e quem lê as mesmas ações de pular, correr e agachar também recebe esses toques.
  - O bot anda em linha reta até cada ponto: não procura caminho em volta de paredes nem gira a câmera. Quando não chega 0,1 m mais perto do ponto em `stuck_after` segundos (1,5 por padrão, no tempo do jogo, que para na pausa do jogo), ele desiste e diz onde e por quê, em vez de tentar resolver a fase. Um personagem que sai da cena depois de o bot assumir também conta como sem avanço.
  - O relatório traz `bot`: `entity` (`{id, name}`), `started_at`, quando o bot assumiu (o começo da cena do personagem mais `start`; ausente quando a corrida mais recente não chegou a assumir, porque a cena do personagem não rodou ou `start` caiu depois do fim do teste, inclusive depois de uma recarga; as corridas anteriores ficam em `earlier`), `reached`, os pontos alcançados, `{index, time, position}`, com `index` contando do 0; `done_at`, quando ele saiu do último ponto, depois da espera e do pulo; `earlier`, as corridas anteriores a uma recarga (veja acima); e `stuck`, `{index, time, position, distance, reason, last_support?}`: o ponto que não alcançou, onde o personagem estava, a quantos metros do ponto e por quê. `reason` é `fell` quando ele caiu (no ar há 1 s ou mais, ou mais de 1 m abaixo de onde pisou por último), `held` quando parou de avançar porque a lógica trava o movimento do personagem (o nó `character.block`, **Bloquear / liberar entrada por motivo**, no canal Movimento), `blocked` quando parou de avançar de outro jeito (contra uma parede, por exemplo), `waiting` quando o objeto de um `wait_for` não chegou ao alcance a tempo e `absent` quando ele, o objeto que o ponto segue ou o objeto do `wait_for` não está na cena que roda. `last_support` (`{id, name}`) é o último objeto em que ele pisou. O `detail` do `stopped_at` diz o mesmo em palavras: `Jogador caiu a caminho do ponto 7 do bot; pisou por último em Plataforma 6`. Antes, a queda vinha como `parou de avançar`, com o personagem dezenas de metros abaixo do piso.
  - Quando a lógica trava o personagem, o relatório traz também `held_by`, os motivos do bloqueio ativos quando o bot o largou, como `["parada"]`. A caminho do último ponto, um bloqueio que começou depois de o bot alcançar o ponto anterior (ou de assumir, num caminho de um ponto só) encerra o caminho no passo em que começa: o bot termina, com `done_at` e `held_by` e sem `stuck`, como quando a lógica trava o personagem ao chegar aonde o caminho leva. Assim, um teste que para na chegada, como um `until` num atributo que a mesma lógica muda, já traz o fim do bot, com ou sem `then_seconds`; antes, ele só terminava `stuck_after` segundos depois do bloqueio (cerca de 1,75 s). O `detail` diz `A lógica travou o movimento de Jogador (motivos: parada) a caminho do último ponto do bot (45); o caminho conta como feito`, e o `until: {"bot": "done"}` para ali. Nos outros casos, como um bloqueio a caminho de um ponto do meio ou um que já estava ativo quando o bot assumiu (uma contagem regressiva), o bot desiste com `held`: `A lógica travou o movimento de Jogador (motivos: contagem) a caminho do ponto 0 do bot, a 5.00 m dele`. Antes, os dois casos vinham como `blocked`, igual a uma parede. `until: {"bot": "done"}` para o teste quando o bot termina o caminho (`stuck`, quando ele desiste; `any`, nos dois casos), logo depois do último passo que ele deu.
  - O mesmo pedido faz o mesmo percurso, e o `check_replay` vale também com o bot.
- **Objetos observados** (`watch`, cada um pelo ID, pelo nome ou por `"$N"`): posição, rotação e escala no mundo, visibilidade e atributos (todos, alguns ou nenhum). Para personagens 3D, também velocidade, chão, postura, apoio e direção do olhar. Cada objeto traz as suas amostras em `samples`, cada uma com o tempo; a última é sempre o estado final, e vêm no máximo uma por passo de 1/60 s e 120 por objeto. Há três jeitos de pedir:
  - `samples`: quantas amostras, espaçadas igualmente pelo tempo que o teste durou: ao longo de `seconds` ou, quando o teste termina antes (pelo `until` ou por um `game.quit`), ao longo do tempo que ele rodou. Cada amostra fica no passo mais próximo do seu lugar; num teste que terminou antes depois de mais de 1024 passos (cerca de 17 s), fica a no máximo 1/1024 da duração do teste desse lugar. Antes, elas se espalhavam por `seconds` mesmo assim, e um teste que parava cedo trazia menos, às vezes só a final.
  - `sample_every`: uma amostra a cada tantos segundos do teste (o relógio do relatório, que a pausa do jogo não para), mais o estado final. Ficam as 120 mais recentes, a final entre elas, porque num teste que para cedo é o fim que interessa; `truncated.samples` conta as que saíram de cada objeto.
  - `samples_at`: amostras nos tempos pedidos, em segundos de 0 (o início, antes do primeiro passo) a `seconds`, cada uma no passo mais próximo, mais o estado final. Tempos repetidos valem uma vez, e os que passam do fim de um teste que terminou antes ficam de fora. Até 119 tempos: com o estado final, são 120 amostras.
  - Se o pedido trouxer mais de um, vale o `samples_at`; sem ele, o `sample_every`; sem os dois, o `samples`. Os outros são ignorados.
- **Relatório:**
  - trocas de cena, com `reload` quando a cena reinicia;
  - logs com o nome do objeto e o nó que os gerou. Uma ação que diz a falha nas saídas `success` e `error`, como o `character.teleport` e os `query.*`, e falha sem nenhum nó ler essas saídas escreve uma linha, uma vez por nó na partida: `Zona de queda · Teleportar com segurança falhou: Destino ocupado; personagem mantido na posição anterior.` A `debug.message` com a entrada `value` ligada escreve o valor depois do texto, como `Motivo: Destino ocupado; …` (números com todas as casas decimais, objetos e superfícies pelo nome, vetores como `(1.5; 0; 2)`): é o jeito de ver no relatório o que um nó calculou, como o `error` de um teleporte. Os avisos de movimento nomeiam o personagem: `Personagem Jogador: Apoio em Elevador liberado sem herdar velocidade…` aparece só quando uma plataforma que gira rápido demais (mais de 20° num passo), muda de escala ou salta de posição deixa alguém sem apoio, não a cada início de cena. Sai uma vez por personagem e plataforma até a cena recomeçar e cita a parte que se moveu: numa ponte de várias tábuas que salta inteira, a ponte, não a tábua sob os pés;
  - um resumo das ações da lógica: cada ação aparece uma vez por nome de objeto, com quantas vezes rodou e quando;
  - sons (`sounds`), inclusive os pedidos no mesmo passo de uma troca de cena, como um som tocado logo antes de reiniciar a fase (o jogo também os toca). Cada um traz `time` e `text`, o nome do som. Um som tocado uma vez (`action.sound`) não tem `kind`, sai sempre no canal `effects` e traz `volume` quando é menor que 1. As mudanças no que toca vêm na mesma lista, só quando mudam algo: `kind` `loop` (um loop que começa ou recomeça, com `started: true`, ou que já tocava e só muda de volume, sem `started`), `stop` (loops parados; `text` `Todos os sons do canal` quando o nó para todos) e `volume` (um volume que muda; `text` é o nome do canal, como `Música`), com `channel` (`music` ou `effects`; `all` numa parada dos dois; `master` no volume geral), `volume` e `fade` (os segundos da transição, quando há). Toda entrada traz `channel` e `effective_volume`, o volume com que o som é ouvido: o `volume` dele vezes o do canal e o geral, como estão no fim do passo em que tocou (o jogo toca o que o passo pediu com os volumes do fim dele). Numa mudança de volume, é o volume com que um som de volume 1 daquele canal é ouvido (o do canal vezes o geral; no `master`, o geral); numa parada, 0. Assim o relatório mostra que um clique tocado depois de os efeitos irem a 0 não é ouvido: `{"text": "Clique", "channel": "effects", "volume": 0.8, "effective_volume": 0}`. Pedir de novo a música que já toca, como ao reiniciar a fase, não aparece, ou aparece sem `started` quando muda o volume: ela segue sem recomeçar. Ficam de fora os sons tocados uma vez e os loops dos efeitos de uma cena que começa e termina no mesmo passo, como numa cena que se reinicia ao começar, porque o jogo não os toca; as mudanças que ela faz na música e nos volumes ficam, porque continuam valendo. Num passo com troca de cena, também fica de fora o loop que começa e já não toca no fim do passo, como um loop dos efeitos tocado logo antes de mudar de cena ou uma música que a cena seguinte troca no mesmo passo;
  - eventos de movimento (pulo, aterrissagem, saída do chão, contato lateral, superfície, postura) e de áreas (entrada e saída);
  - o percurso do bot (`bot`), quando o pedido tem um;
  - a pausa do jogo: `pauses` lista cada mudança, `{time, paused}`, com o novo estado (só quando houve alguma), e `paused` diz se o jogo terminou pausado;
  - a câmera do jogo no fim;
  - a interface do jogo no fim (`ui`), na ordem em que é desenhada: cada elemento com o tipo, se está visível, o retângulo na vista do jogo, o texto como aparece (com o valor ligado, como `Tempo: 12.50`; para ler `Tempo: 01:23.45`, a lógica formata os segundos com o nó `text.time` e grava o texto num atributo de texto ligado ao elemento), o tamanho da letra em pixels da vista (`text_size`, em todos menos as imagens), o alinhamento dos textos (`text_align`: `Left`, `Center` ou `Right`), o quanto uma barra está cheia (`fraction`), se um botão dá para clicar e, num elemento visível, `covered_by`: o nome do elemento visível mais de cima, desenhado depois dele (numa camada maior, ou na mesma camada e depois na cena), cujo retângulo cobre o centro dele, o que uma pessoa vê ali. Um clique nesse ponto ainda vai para o botão mais de cima sob ele, porque imagens e textos não recebem cliques; para saber qual, clique por `point`. O retângulo é medido numa vista de `width` × `height` pixels (por padrão, a janela do jogo), que o relatório repete em `view_size`. Junto vem `cursor_free`: se o cursor de uma pessoa estaria livre no fim, para clicar nos botões, porque a lógica o mostrou (`game.cursor`), porque o jogo está na pausa dele ou porque a câmera ativa não gira com o mouse. `ui: false` deixa os dois fora do relatório;
  - as variáveis do jogo no fim (`variables`), pelo nome, com o valor e o tipo (`{"Moedas": {"Number": 12}}`); o valor de uma chave vem como `Nome · chave`, como `Pontos · Cena 2`. Vêm até 300 valores: primeiro o valor único de cada variável, depois os das chaves, em ordem de nome; `truncated` conta os que ficaram de fora. Num projeto sem variáveis, o campo não vem;
  - o que toca no fim (`audio`): `music` (a música, se houver), `loops` (os loops dos efeitos) e `volumes` (`master`, `music` e `effects`), cada som com `asset`, `name` e `volume`. Sem loops e com todos os volumes em 1, o campo não vem;
  - com scripts, o custo de cada arquivo (`script_time`): `{path, calls, steps, p50_us, max_us, most_entries, warning?}`. `calls` são as chamadas dele (eventos e temporizadores); `steps`, os passos em que rodou (o começo de uma cena conta como um); `p50_us` e `max_us`, os microssegundos desses passos (metade levou `p50_us` ou menos, e o mais lento, `max_us`), tempo de relógio, que muda de uma execução e de um PC para outro e nunca entra no `state_hash`; `most_entries`, o máximo de entradas de tabela que ele converteu entre o Luau e a engine num passo (a memória do script lida e gravada de volta, as mensagens); `warning`, quando passa de 1024, com o que fazer. Sem scripts, o campo não vem;
  - com scripts, os erros deles (`script_errors`): cada erro uma vez por objeto e linha, `{object?, path?, line?, text, count, stopped?}`, com o objeto (`{id, name}`; nenhum num script que não carregou), o arquivo e a linha (sem `path` no que a engine diz dos scripts como um todo, como o limite de trabalho dos scripts no passo), a linha do log do primeiro (`text`), quantas vezes aconteceu ali (`count`; um erro no `on_step` conta um por passo, e o log mostra só o primeiro) e `stopped: true` quando um limite parou o script naquele objeto. Os erros de uma cópia removida durante o teste saem com ela. Sem erros, o campo não vem;
  - o progresso salvo: `saves` lista cada `save.write` e `save.clear` do teste, `{time, kind: "write" | "clear", values}`, com os valores salvos (só na gravação) no formato de `variables`, e `save` traz o progresso no fim, no mesmo formato da entrada `save`. Para testar a volta do jogador, passe o `save` de um relatório no `save` do teste seguinte: na segunda corrida, por exemplo, um recorde menor substitui o salvo. Sem progresso no fim (nada salvo, ou apagado), `save` não vem. Cada gravação em `saves` e o `save` trazem até 300 valores; `values_truncated` (na gravação) e `truncated.save` contam os que ficaram de fora.

**Repetir um teste.** O mesmo pedido dá o mesmo jogo; veja [Determinismo](#determinismo).

**Eventos.** Os eventos entram no relatório no momento em que o jogo os dispara. Por isso aparecem mesmo quando a lógica, no mesmo passo, remove a área ou o objeto (moedas, pontos de controle, zonas de morte) ou troca de cena. Uma área, 2D ou 3D, que a lógica desliga (`action.component` com `collider`) não gera saída para quem estava dentro, como no jogo; ao ser religada, quem está dentro entra de novo, numa nova ativação (um `action.damage` de uma vez por ativação acerta outra vez), mesmo que a área tenha sido desligada e religada no mesmo passo.

**Mudanças no relatório em relação à 0.5.0:**
- `scene_changes` passou de `{time, text}` para `{time, scene, name, reload}`.
- Os logs saem sem IDs no texto e ganham `object` e `node`.
- `actions` passou a ser um resumo por padrão (veja abaixo); a lista completa vem com `actions: "all"`.
- As amostras de `watch` só trazem os campos pedidos em `fields`, e a rotação no mundo é lida como no `oxy_scene` (um objeto girado 120° lê `[0, 120, 0]`, não `[180, 60, 180]`).
- `oxy_simulate` e `oxy_screenshot` recusam `width` e `height` fora de 16–4096, e o texto do `oxy_screenshot` nas vistas do jogo passou a ser JSON (tempo, cena e câmera usada).
- `samples` traz exatamente o número pedido; antes, quando os passos não se dividiam igualmente, vinha uma amostra a mais.
- O `detail` de um `stopped_at` por evento passou de `land de Jogador (Pouso)` para `Jogador aterrissou em Pouso`, e o tipo do evento ganhou o campo `kind`.
- O relatório traz `seed`, a semente dos sorteios, e `state_hash`, o resumo do estado no fim; as cópias do `action.spawn` mantêm os IDs de uma execução para outra.
- Um `click` num elemento da interface oculto é ignorado, com uma linha no log, como no jogo; na 0.5, o clique chegava à lógica. O relatório traz `paused` e, quando o jogo pausou, `pauses`.
- As entradas de `sounds` continuam com `time` e `text` e ganham `kind`, `started`, `channel` (em todas, `effects` nos sons tocados uma vez), `volume`, `effective_volume` e `fade`; o relatório ganha `audio`, e o `until`, `sound`.
- Num teste que termina antes (pelo `until` ou por um `game.quit`), as `samples` se espalham pelo tempo que ele rodou, e há `sample_every` e `samples_at`.
- O `stopped_at` de `quit` traz `object` e diz no `detail` qual objeto pediu para sair.
- O pedido aceita `bot`, que o relatório devolve com o percurso, e o `until` ganha `bot`. O texto do `oxy_screenshot` também traz `bot`. O personagem do bot pode ser de qualquer cena (o bot assume quando ela roda, e `started_at` diz quando), e o `stuck` traz `reason` e `last_support`.
- Com `ui`, o relatório traz `cursor_free`, se o cursor de uma pessoa estaria livre no fim; o `play` do `oxy_status` também.
- O `click` aceita o nome do objeto, recusa antes de rodar um objeto que o projeto não tem e registra no log o clique num objeto de outra cena; a cena inicial (`scene`) e o `until.scene_change` aceitam o nome da cena.
- O `bot` ganhou o `wait_for` nos pontos e os motivos `held` e `waiting`, com `held_by`; um bloqueio da lógica a caminho do último ponto encerra o caminho com `done_at`. O `until` ganhou `then_seconds`, e o `stopped_at`, `ended_at`. O `click` aceita `point`, e cada elemento do `ui` traz `covered_by` quando outro o cobre.
- A vista do jogo passou a ter, por padrão, o tamanho da janela do jogo, e não 960×540, e o relatório traz `view_size`. O bot recomeça o caminho quando a cena do personagem começa de novo, com as corridas anteriores em `earlier`, e termina no passo em que a lógica o trava a caminho do último ponto. O personagem e os pontos do bot, o `watch`, o `spawn` e os objetos do `until` aceitam o nome do objeto (veja **Objetos pelo nome**).
- Uma falha que nenhum nó lê (`success` e `error` desligados) aparece nos logs, uma vez por nó, e a `debug.message` ganhou a entrada `value`. O `character.teleport` deixou de pôr um personagem dentro de outro: dois corpos em pé no mesmo eixo, ou quase, eram lidos como espaço livre; agora o corpo de outro personagem conta como ocupado quando os grupos de colisão dos dois corpos se aceitam (como no movimento), e a busca acha espaço ao lado ou recusa.

**Resumo das ações.**
- A lógica que roda a cada passo (`event.step`), como cronômetros, fica fora do resumo, a menos que o agente peça (`actions_filter: {exclude_operations: []}`).
- A troca de cena (`action.scene`) sempre aparece, mesmo quando um `event.step` a dispara. Assim, cada troca de cena tem a ação que a explica.
- Objetos com o mesmo nome dividem uma linha, como as cópias criadas durante o jogo (`Bala (cópia)`).
- `actions: "all"` lista cada ação com o horário e usa o mesmo filtro. Na 0.5.0, a lista completa era o padrão.
- Cada lista do relatório guarda as 300 entradas mais recentes; no resumo, ficam as 300 linhas com atividade mais recente. `truncated` conta o que ficou de fora.

## Determinismo

O mesmo pedido ao `oxy_simulate` dá o mesmo jogo: os passos têm duração fixa (1/60 s), e o que poderia mudar de uma execução para outra segue regras.
- **Semente** (`seed`): os sorteios do nó `random.number` (**Sortear número**, em Ações) vêm da semente, um inteiro de 0 a 9007199254740991 (0 por padrão). O relatório repete a semente em `seed`. Para ver outros sorteios, mude a semente; a mesma semente repete os mesmos números.
  - Cada nó `random.number` tem a sua sequência: acrescentar outro sorteio na lógica não muda os números dos que já existiam. O nó `random.seed` (**Definir semente aleatória**) troca a semente durante o jogo e recomeça todas as sequências.
  - O teste do editor e o jogo exportado começam com uma semente nova a cada partida.
- **Cópias:** as cópias do `action.spawn` recebem os mesmos IDs a cada execução, qualquer que seja a semente, e cada cópia tem os seus, também nos nós e nas animações dela. Os IDs têm o formato dos outros, então os logs e os eventos continuam trazendo o nome da cópia (`Bala (cópia)`). Na 0.5, as cópias recebiam IDs novos a cada execução.
- **Estado no fim** (`state_hash`): 16 dígitos hexadecimais que resumem o estado do jogo no fim do teste: a cena, o tempo, cada objeto (posição, atributos, componentes, lógica), os personagens, a câmera, as tarefas pendentes, os sorteios, as variáveis do jogo, o progresso salvo e o que toca (a música, os loops e os volumes). Dois testes com o mesmo `state_hash` terminaram no mesmo estado, então basta compará-lo para saber se uma mudança alterou o resultado. A semente também entra na conta: sementes diferentes dão `state_hash` diferentes mesmo sem sorteios. Os IDs também: os objetos que o `setup` cria recebem IDs novos a cada pedido e mudam o `state_hash`.
- **Conferir a repetição** (`check_replay: true`): roda uma segunda cópia do jogo ao lado da primeira, com as mesmas entradas e a mesma semente, e compara o estado das duas a cada passo. O relatório ganha `replay: {identical, steps, first_difference}`:
  - `identical` diz se as duas ficaram iguais até o fim, e `steps` quantos passos foram comparados (o início também é comparado, antes do primeiro passo);
  - `first_difference` diz onde se separaram: o tempo, o objeto (`object`, com o nome) e a parte (`part`): `transform`, `visible`, `attributes.Vida`, `document` (o resto do objeto), `character`, `animation`… ou, sem objeto, `tasks`, `random` (os sorteios), `variables.Moedas` (uma variável do jogo, pelo nome), `save` (o progresso salvo), `audio` (o que toca), `camera`…; `exists` quando só uma das cópias tem o objeto, e `order` quando as duas o têm, em outra ordem na cena.
  - Uma diferença é um defeito da engine, não da lógica do jogo. A conferência custa algumas vezes o tempo de um teste comum. O `oxy_screenshot` aceita o mesmo `check_replay` e traz `replay` no texto.
- **Conferir a VM recriada** (`check_vm_reset: true`, com scripts): roda outra cópia ao lado, com as mesmas entradas e a mesma semente, que joga fora a VM do Luau dos scripts e a cria de novo a cada 30 passos (e em passos sorteados pelo número do passo), mantendo o estado do jogo, e compara as duas a cada passo. O relatório ganha `vm_reset`, lido como o `replay`: `{identical, steps, first_difference?, error?}`. `identical: false` quer dizer que um script guarda estado na VM entre as chamadas (uma tabela do módulo que ele enche, um valor guardado num local do módulo), que uma recarga, uma restauração e a rede da 0.8 perderiam: guarde-o num atributo ou em `Modulo.state`. `error` diz por que a conferência parou antes, como um script que não carregou na VM nova. Até a etapa 4 da 0.7, a opção existia só por dentro, e o `oxy_simulate` a ignorava.

## Criar um projeto com `oxy_new_project`

Para começar um jogo do zero, o agente cria o projeto como o **Projeto → Novo projeto** do editor seguido do primeiro **Salvar**, mas só quando você pede, na pasta que você indicar.

- **Pedido:** `folder`, o caminho completo da pasta do projeto num disco deste computador (`C:\...`); `name`, o nome do projeto; e `scene: {kind, name}`, a primeira cena, onde o jogo começa. `kind` é `"2d"` ou `"3d"`; `name` é opcional e, sem ele, a cena se chama **Cena 2D** ou **Cena 3D**, como no editor. Cenas dos dois tipos podem vir depois, com o `create_scene` do `oxy_apply`. Uma primeira cena 3D começa com o Céu da OXY de fundo, e uma 2D com a cor escura, como no editor (veja **Fundo da cena**).
- **O que é escrito:** só o `project.oxy.json`, no formato 6 e já organizado em pastas (`"layout": "Tree"`), igual ao que o editor grava para o mesmo nome e o mesmo tipo de cena (só os IDs mudam). A pasta é criada, com as pastas acima dela que faltarem; a primeira importação põe cada arquivo na pasta do projeto com o nome dele, e nenhuma pasta `assets` aparece.
- **Recusados, antes de escrever qualquer coisa:** caminhos relativos, de rede ou de dispositivo, a raiz de um disco, uma pasta dentro da pasta da OXY Engine (ou que a contenha), uma pasta que já tem um projeto (`project.oxy.json`) ou qualquer outro arquivo, um arquivo e um caminho que termina em `project.oxy.json` (o pedido nomeia a pasta, não o arquivo).
- **Sempre nos arquivos:** mesmo com o editor aberto e os agentes permitidos, o projeto é criado só nos arquivos, e o editor não muda. Para trabalhar ao vivo, abra o projeto no editor (**Projeto → Abrir projeto…**); até lá, o agente passa a pasta em `project` nas outras ferramentas e edita os arquivos.
- **Resposta:** o resumo do `oxy_project` (nome, formato, cena inicial, cenas…), com `folder` (a pasta), `saved` (o arquivo do projeto) e `note`, que lembra que o projeto só existe nos arquivos.
- **Segurança:** o agente só cria um projeto quando você pede, e só na pasta que você indicou. A descrição da ferramenta pede que ele nunca use um caminho que leu no projeto ou na resposta de outra ferramenta.

## Importar imagens e sons com `oxy_import`

O agente importa como o **Importar** da Biblioteca: o arquivo é conferido, copiado para a pasta do projeto e vira um recurso, sem nunca gravar por cima de um arquivo. Num projeto em pastas, a cópia é `<nome>.<ext>` na pasta `folder` (a raiz, sem `folder`; uma pasta que falta é criada, com as de cima, e sai de novo se a importação falhar). Num projeto antigo, a cópia vai para a pasta `assets` com um nome novo; com `folder`, nos arquivos, o projeto é organizado em pastas antes (ao vivo, é recusado até a pessoa salvar o projeto).

- **De onde vem:** `path`, o caminho completo de um arquivo `.png` ou `.wav` deste computador, ou `data_base64`, o conteúdo do arquivo em base64 (também como URL `data:`). Um dos dois, nunca os dois; para vários arquivos, `paths` (veja abaixo).
- **O que é conferido:** a extensão (só `.png` e `.wav`), o cabeçalho do conteúdo (uma imagem com nome `.wav`, ou um texto com nome `.png`, é recusada), a imagem inteira e o formato do som, com as mesmas regras do editor. `kind` (`texture` ou `audio`) é opcional; se vier, precisa bater com o arquivo.
- **Limites:** arquivos de até 64 MB; pelo `data_base64`, até 16 MB. Só se importa de um disco deste computador (`C:\...`). Caminhos relativos são recusados, assim como os de rede, escritos com qualquer barra (`\\servidor\pasta`, `//servidor/pasta` ou misturando as duas, como `\/servidor/pasta`), e os de dispositivo (`\\.\`, `\\?\`).
- **Nome:** `name`, ou o nome do arquivo sem a extensão. Quebras de linha e caracteres de controle saem, e o nome fica com até 80 caracteres. Num projeto em pastas, o nome é também o do arquivo e é único por tipo no projeto inteiro: um nome que outro som (ou outra imagem) já tem, em qualquer pasta, é recusado com um nome livre sugerido (`Já existe o som "Pulo" (Sons/Pulo.wav): … passe outro name (Pulo 2 está livre)`); um `name` que o Windows não aceita é recusado com o motivo, e o nome tirado do arquivo é ajustado.
- **Arquivo que já está no projeto:** um `path` dentro da pasta do projeto (um arquivo que você pôs lá pelo Explorer, por exemplo) é registrado onde está, sem cópia, e a resposta traz `in_place: true`. Um `name` ou uma `folder` diferentes do arquivo são recusados: renomear e mover são do `oxy_apply`.
- **Aplicar:** `apply_to` põe a imagem num objeto da cena (`scene`, ou a cena aberta no editor; nos arquivos, a cena inicial): na imagem dele, se for um elemento da interface, ou no material. Um sprite fica com a proporção da imagem, mantendo a altura, como no editor. Um grupo ou uma câmera, sem forma, é recusado. Sons não se aplicam a objetos: os nós `action.sound`, `action.sound_loop` e `action.sound_stop` usam o som pelo ID do recurso, no parâmetro `asset`.
- **Resposta:** `{asset, name, kind, path, width, height}` para imagens e `{asset, name, kind, path, seconds}` para sons, com `applied_to` quando a imagem foi aplicada e `in_place` quando o arquivo já estava no projeto; `path` é onde o arquivo ficou. Sem `name`, um arquivo com nome de ID (`1d76fcf6-74c0-40ed-8168-64ef00b254fb.wav`, como os do layout antigo) dá um recurso com esse nome, e a resposta traz `warning`, que pede um nome que a pessoa reconheça (com o `rename_asset`, ou importando de novo com `name`).
- **Vários de uma vez:** `paths` importa vários arquivos numa chamada só, no lugar de `path` e `data_base64`: até 32, e até 256 MB juntos. Cada item é o caminho completo do arquivo ou `{path, name?, kind?, apply_to?, folder?}`, com as opções daquele arquivo; `name`, `kind` e `apply_to` vão dentro do item, não ao lado de `paths` (o `scene` fica ao lado, para os `apply_to`, e uma `folder` ao lado vale para os itens que não dizem a sua). Cada arquivo passa pelas mesmas conferências de um sozinho, e todos são lidos e conferidos antes de qualquer cópia: ou entram todos, ou nenhum. O erro diz qual arquivo falhou, contando do 0, como em `paths[1] (o 2º arquivo): O conteúdo não é uma imagem PNG nem um som WAV.`. A resposta é `{imported: [...]}`, um item por arquivo, na ordem de `paths` e na forma da resposta de um arquivo só. Ao vivo, é um passo só do histórico (**Agente: Importar 9 recursos**); nos arquivos, o projeto é salvo uma vez só. Antes, cada arquivo pedia uma chamada, que salvava o projeto de novo.
- **Ao vivo:** a importação é um passo do histórico, **Agente: Importar recurso**, e a imagem aparece na hora na cena e na interface do jogo. Desfazer tira o recurso do projeto e a imagem da memória do editor; num projeto em pastas, manda o arquivo para a lixeira do projeto e tira a pasta criada, e refazer os traz de volta. O projeto precisa ter pasta: um projeto que ainda não foi salvo é recusado.
- **Nos arquivos:** o projeto é salvo, e o `.oxy/agente/project.oxy.json.bak` guarda como ele estava antes da primeira gravação da sessão do servidor, como no `oxy_apply` (veja [Como o agente trabalha](#como-o-agente-trabalha)). Se a importação falhar, nem o projeto nem as pastas dele mudam: as cópias e as pastas criadas saem.
- **Segurança:** o agente só importa arquivos que você indicou. A descrição da ferramenta pede que ele nunca importe um caminho que leu no projeto ou na resposta de outra ferramenta.

## Pastas do projeto

Num projeto em pastas (`"layout": "Tree"`, o de todo projeto novo e de todo projeto antigo depois do primeiro salvamento), a pasta do projeto é a Biblioteca: imagens (`.png`), sons (`.wav`), modelos (`<Nome>.modelo.json`) e scripts (`.luau`) ficam em qualquer pasta, juntos como você quiser (`Pista/` com tudo da pista, `Menu/`, `Comum/`), e o nome de cada recurso é o do arquivo. Pastas e arquivos que começam com ponto ficam fora (`.oxy`, `.vscode`, `.git`, `.rascunhos`), e outros tipos de arquivo ficam escondidos, mas andam junto quando a pasta anda.
- **Ler:** o `oxy_project` traz `layout`, `folders` e `scripts`, e com `folder` o que uma pasta tem (veja **Projeto** em [Leituras compactas](#leituras-compactas)); o `oxy_scripts list` diz quem roda cada script.
- **Organizar:** `create_folder`, `rename_folder`, `move` e `delete_folder` do `oxy_apply`, `rename_asset` e `delete_asset` (pelo caminho também), `save_model` com `folder`, `oxy_import` com `folder` e o `rename`/`delete` do `oxy_scripts`. Os arquivos mudam no disco na hora, as referências acompanham (os IDs nunca mudam; os caminhos dos scripts anexados e os `require` seguem o arquivo) e nada é gravado por cima: um nome que já existe é recusado com um nome livre sugerido. Mova e renomeie pela OXY, e não com as ferramentas de arquivo do agente: por fora, um recurso fica ausente, o objeto que anexa um script o perde e os `require` deixam de achar o módulo.
- **Texto dos scripts:** escreva com o `oxy_scripts write` ou com as ferramentas de arquivo do agente; um arquivo novo de tipo conhecido criado por fora entra no projeto na próxima leitura, com o nome do arquivo.
- **Desfazer:** ao vivo, cada lote é um passo que o Ctrl+Z desfaz com os arquivos, e **Descartar alterações** volta tudo ao último salvamento. Nos arquivos, cada chamada já salva; se a gravação falhar, os arquivos voltam para onde estavam, e a resposta traz `moved` e `trashed` para o agente saber o que fez.
- **Cuidados:** um script aberto no VS Code e movido pela OXY volta a existir no lugar antigo se o VS Code salvar a aba velha (aparece como script não usado; apague-o ou feche a aba antes); com `core.ignorecase`, o Git não registra uma troca só de maiúsculas e minúsculas; e pastas sincronizadas (OneDrive, Dropbox) podem criar cópias de conflito e disputar arquivos renomeados.

## Exportar o jogo com `oxy_export`

O agente exporta o jogo como o **Projeto → Exportar jogo…** do editor (veja [Exportar o jogo](guia-do-editor.md#exportar-o-jogo)), mas só quando você pede, para a pasta que você indicar.

- **Destino:** `destination`, o caminho completo de uma pasta de um disco deste computador (`C:\...`). O jogo vai para `<destination>\<Nome do jogo>`, com `<Nome do jogo>.exe`, a pasta `data`, as licenças e um `LEIA-ME.txt`. O nome do jogo é o título de `game` no `oxy_project` (o nome do projeto, se o jogo não tiver título), sem os caracteres que o Windows não aceita em nomes de arquivo; o título, a janela e a tela cheia mudam pelo comando `set_game_settings` do `oxy_apply`.
- **Recusados:** caminhos relativos, de rede ou de dispositivo, a raiz de um disco, uma pasta do jogo dentro da pasta do projeto ou da OXY Engine (ou que contenha uma delas) e uma pasta do jogo que já existe com outros arquivos ou com a exportação de outro jogo.
- **Substituir:** uma exportação anterior do mesmo jogo, reconhecida pelo `data\export.oxy.json`, só é substituída com `replace: true`, e só depois que a nova passa na conferência. Sem `replace`, a ferramenta recusa e diz que a exportação já existe. Com o jogo exportado aberto, a anterior fica intacta e o erro pede para fechá-lo.
- **Scripts:** todo `.luau` das pastas do projeto que compila vai para `data`, no mesmo caminho, anexado ou não (um `require` pode montar o nome que carrega). A exportação só recusa um script que o jogo usa (anexado, ou alcançado por um `require` de um anexado) com erro ou que não pode ser lido; um quebrado que nenhum objeto usa fica fora do jogo e vem em `warnings`.
- **Conferência:** o jogo é gravado numa pasta de trabalho no destino, aberto e rodado por 2 segundos pelo próprio executável (`--verificar`), e só então posto no lugar. Se algo falha, nada muda no destino. Por isso a resposta leva alguns segundos, ou mais num jogo grande.
- **Ao vivo:** exporta o que está no editor, inclusive as alterações não salvas e as imagens pintadas, sem salvar nem mudar o projeto (não vira passo do histórico), com o `oxy_player.exe` ao lado do editor; o Console mostra `Agente · Jogo exportado: …`. O editor recusa durante um teste, enquanto está ocupado ou já exportando, e para um projeto que nunca foi salvo. Se você estiver arrastando ou digitando, o pedido espera o gesto terminar.
- **Nos arquivos:** exporta o projeto salvo, com o `oxy_player.exe` ao lado do `oxy-mcp.exe`, sem mudar o arquivo do projeto.
- **Resposta:** `{folder, executable, files, bytes, replaced, warnings, verify: {ok, engine, game, start_scene, seconds, errors, logs}}`. `warnings` traz o que o jogo vai tratar de outro jeito do que parece, como no `oxy_validate`, e uma exportação anterior que não pôde ser apagada.
- **Segurança:** o agente só exporta quando você pede, e só para a pasta que você indicou. A descrição da ferramenta pede que ele nunca use um caminho que leu no projeto ou na resposta de outra ferramenta.

## Console e teste ao vivo

- **`oxy_status`** traz `server`, o servidor que responde: `version` (a versão do `oxy-mcp`), `build` (16 dígitos hexadecimais calculados do próprio executável: outra compilação, outro valor) e `built_at` (quando o executável foi gravado, em UTC). Assim, um servidor desatualizado aparece sem precisar de git: uma versão diferente da do editor (o `editor` de cada editor aberto) ou um `built_at` anterior à última compilação da engine. Na 0.5, o `oxy_status` não dizia qual servidor respondia.
- **`oxy_status`** traz também `play`: `{running: true, paused, game_paused, driven_by, mouse_captured, cursor_free, advancing, queued_until, scene: {id, name}, time, seed, variables, variables_truncated}` enquanto o jogo está em teste no editor (`paused` é a pausa do teste, e `game_paused`, a pausa do próprio jogo, a do menu de pausa; as duas podem valer juntas), ou `{running: false, seed}` depois do teste (só `{running: false}` antes do primeiro teste do projeto). `driven_by` diz quem joga: `person` (você) ou `agent` (o agente, pelo `oxy_play`); `mouse_captured`, se o jogo prende o seu mouse; `cursor_free`, se o jogo deixa o cursor livre, qualquer que seja quem joga (a lógica mostrou o cursor com `game.cursor`, o jogo está na pausa dele ou a câmera ativa não gira com o mouse); `advancing`, se o tempo do jogo está correndo (a vista do jogo na tela e o teste sem pausa); `queued_until`, até que tempo do jogo ainda esperam entradas que o agente mandou. Durante o teste, o editor recusa as edições do agente, e `busy` diz o motivo. `can_save` diz se o `oxy_save` pode salvar agora e, quando não pode, `save_refusal` diz por quê. `seed` é a semente dos sorteios do teste atual ou do último, nova a cada vez que você joga: no `oxy_simulate`, a mesma semente dá a cada nó `random.number` os mesmos números, na mesma ordem. `variables` traz as variáveis do jogo naquele momento do teste, como no relatório do `oxy_simulate`, até 300 valores (só quando o projeto tem variáveis); `variables_truncated` conta os que ficaram de fora.
- **`oxy_status`** traz em `project`, além do nome, do caminho e das alterações não salvas, o `layout` (`tree` ou `legacy`), `conversion_pending: true` num projeto antigo que o próximo salvamento organiza em pastas e `scripts`: `{files, objects, errors?, errors_total?, checker}`, os arquivos `.luau` da pasta do projeto, quantos objetos anexam um script e o que impede os scripts de rodar, como o `oxy_scripts check` acha (um script que não carrega, com o arquivo e a linha, e um arquivo que um objeto anexa e a pasta não tem), os 10 primeiros. Só o `oxy_status` confere os scripts; as outras ferramentas leem o estado do editor sem isso. A explicação de `how_targets_work` lembra que gravar um script vale na hora, também durante um teste, que o recarrega, e que as edições do documento esperam o teste parar.
- **`oxy_console`** lê o Console do editor aberto. Cada linha vem com `seq`, `origin` e `text`:
  - `editor`: mensagens do editor; `warning: true` marca as que também viraram aviso;
  - `agente`: as edições do agente e os erros delas;
  - `jogo`: os logs do seu teste, como as mensagens de diagnóstico (`debug.message`, com o valor ligado à entrada `value`) e os erros dos nós, com o objeto (`object: {id, name}`) e o nó (`node`) de onde vieram, e a linha `<objeto> · <nó> falhou: <motivo>` de uma ação cuja falha nenhum nó lê, uma vez por nó no teste; os `print`, `warn` e erros dos scripts trazem `script: {path, line}`;
  - `logica`: as ações da lógica que o teste rodou, como o Console as lista (`0.500 s · Porta · Reproduzir WAV`), com o objeto, o nó e a operação.
  - Uma linha do editor ou do agente que aponta a linha de um script, como `Script não recarregado: Pista/porta.luau:12: …` ou um aviso do `attach_script`, também traz `script: {path, line}`, para o agente abrir o arquivo na linha com o `oxy_scripts read`.
- `seq` cresce enquanto o editor fica aberto. A resposta traz `last_seq`; passando-o em `since` na leitura seguinte, vêm só as linhas novas. `origin` filtra por uma origem ou uma lista, e `limit` (50 por padrão) fica com as linhas mais recentes; `omitted` conta as que ficaram de fora.
- Ao reabrir o editor, a numeração recomeça, com outra `session` na resposta. Quando a `session` muda, o agente lê de novo sem `since`. Um `since` maior que o `last_seq` (guardado de antes de o editor fechar) não esconde as linhas novas: a leitura começa da linha mais antiga guardada, e a resposta traz `reset: true`.
- As linhas do jogo e da lógica continuam lá depois que o teste para: quando você diz "apertei J e nada aconteceu", o agente lê o que o seu teste registrou. O agente guarda as 1000 linhas mais recentes, e a lógica guarda as suas 300 à parte, para a lógica que roda a cada passo não empurrar o resto para fora. Limpar o Console limpa também o que o agente lê.
- Nos arquivos, sem editor aberto, não há Console: a ferramenta explica que só funciona ao vivo. Para testar sem editor, use o `oxy_simulate`.

## Teste ao vivo pelo agente

O `oxy_play` deixa o agente testar o jogo no editor enquanto você assiste, por exemplo para mostrar um defeito ou uma fase funcionando. O teste é o mesmo do **Jogar**, com uma diferença: o agente nunca prende o seu mouse nem lê o seu teclado, e o jogo continua quando a janela do editor fica em segundo plano (o seu teste pausa quando o editor perde o foco, a menos que **Continuar o teste quando a OXY perde o foco** esteja ligada em **Preferências do editor › Teste**; aí ele segue sem o seu teclado e mouse).
- `action` diz o que fazer:
  - `start` inicia um teste na cena de `scene` (pelo ID ou pelo nome) ou, sem ela, na cena aberta no editor, como o **Jogar**. O editor mostra a Cena com o jogo.
  - `pause` pausa o teste, seja o do agente ou o seu.
  - `resume` retoma um teste do agente que está pausado.
  - `stop` para um teste que o agente joga.
  - `input` manda entradas ao teste que o agente joga, no formato das `inputs` do `oxy_simulate` (`press`, `release`, `movement`, `look`, `click`, `escape`, com as ações e os objetos clicados pelo ID ou pelo nome). O clique por `point` é recusado, porque a vista do jogo no editor tem o tamanho do painel: clique pelo objeto. O `at` conta segundos do tempo do jogo a partir de agora ou, se ainda há entradas esperando, a partir da última delas (`queued_until`): os lotes entram em fila, na ordem. Se uma entrada do lote é inválida, nenhuma entra. É recusado com o teste pausado.
- O seu teste é seu, desde o **Jogar** ou depois de **Assumir** ou **Retomar**: o agente pode pausá-lo, mas não retomá-lo, pará-lo nem mandar entradas a ele.
- Cada resposta traz o `play` novo, como no `oxy_status`.
- Enquanto o agente joga, a barra do editor mostra **Agente jogando**, as Propriedades explicam que um agente está jogando e a barra de status mostra **Agente jogando**. O botão **Assumir** passa o teste para você: o mouse e o teclado voltam a controlar o jogo, e as entradas que o agente ainda tinha mandado são descartadas. **Retomar** também passa um teste pausado para você.
- Uma pausa, uma troca de cena ou um reinício descartam as entradas que ainda esperavam, e as teclas e o movimento que estavam pressionados param.
- O Console mostra, com a origem **Agente**, quando o agente inicia, pausa, retoma ou para o teste.

## Salvar ao vivo

Por padrão, o agente não salva: quem salva é você. Ligando **Permitir que agentes salvem**, em **Preferências do editor**, o agente pode salvar com o `oxy_save`:
- O agente salva tudo o que não foi salvo, inclusive as suas alterações, como o **Salvar** do editor.
- Antes de cada salvamento, o arquivo como estava é guardado em `project.oxy.json.agente.bak`, ao lado dele: ao vivo, a cópia é a de antes daquele salvamento (nos arquivos, a cópia é `.oxy/agente/project.oxy.json.bak`, a de antes da primeira gravação da sessão do servidor). O Console mostra `Agente · Salvo: …`.
- Um projeto do layout antigo é organizado em pastas nesse salvamento, como no primeiro **Salvar** (veja [Como o agente trabalha](#como-o-agente-trabalha)): a resposta traz `converted`, ou, quando ele continua no layout antigo, o motivo em `warnings`.
- O editor recusa e explica o motivo quando a opção está desligada, durante um teste, enquanto está ocupado (modelagem em prévia, pose provisória, uma decisão sobre alterações não salvas) e quando salvar abriria a escolha de pasta: um projeto que nunca foi salvo ou uma cópia de exemplo. O `oxy_status` mostra antes se o agente pode salvar (`can_save` e `save_refusal`).
- Nos arquivos, cada `oxy_apply` e cada `oxy_import` já salva o projeto: o `oxy_save` só explica isso.

## Imagens com `oxy_screenshot`

- **Vista do editor** (`view: "editor"`, ao vivo): o que aparece na vista do editor. Com `colliders: true`, o editor desenha a mesma vista de novo com os colisores por cima, como na vista de colisores, sem mexer no que aparece na tela. Durante um teste do jogo, mostra o jogo como você o vê: a câmera do jogo com a interface do jogo (textos, imagens, botões e barras) por cima.
- **Câmera do jogo** (`view: "game"`, o padrão nos arquivos): roda o jogo numa cópia por `seconds` (0 é o primeiro quadro), com as mesmas `inputs`, `setup`, `spawn`, `until`, `bot`, `seed` e `save` do `oxy_simulate`, e captura pela câmera do jogo, com a interface do jogo desenhada por cima, como no jogo. O texto traz a interface em `ui`, como no `oxy_simulate`, com os mesmos retângulos da imagem, e `cursor_free`; `ui: false` deixa os dois de fora, o que encurta a resposta em capturas repetidas, mas a imagem continua com a interface. As outras vistas não desenham a interface.
- **Câmera livre** (`view: "free"`): uma câmera em `eye` olhando para `target`, que é um ponto ou um objeto, pelo ID ou pelo nome (o centro da forma dele ou, sem forma, a posição), com `fov` em graus (60 por padrão). Só em cenas 3D.
- **De cima e de lado** (`view: "top"` e `view: "side"`): vistas ortográficas, sem perspectiva, que enquadram os objetos de `ids` e seus filhos, ou tudo o que tem forma. De cima, o -Z fica para cima na imagem. De lado, a câmera olha ao longo do -Z ou, quando a parte enquadrada é mais funda (Z) do que larga (X), ao longo do -X, para o lado comprido ocupar a imagem. Em cenas 2D, as duas mostram o plano da cena.
- **Colisores** (`colliders: true`): desenha os colisores sólidos em verde e as áreas em amarelo, inclusive de objetos invisíveis, como pontos de controle.
- **Tamanho:** a imagem tem `width` × `height` pixels, de 16 a 4096; sem eles, o tamanho da janela do jogo, como no `oxy_simulate` (veja **Tamanho da vista**).
- O texto da resposta diz o tempo, a cena, `view_size` (o tamanho da imagem) e a câmera usada (posição, direção e o campo de visão ou a largura e a altura vistas, em metros) e, com um bot, o percurso dele (`bot`).

## Limites desta versão

O que a 0.6 ainda não faz, e o que o agente faz no lugar. A rede, as entradas por jogador e os escopos de variáveis vêm na 0.7 (veja o [roadmap](roadmap.md)).

**O jogo**
- **Uma entrada só:** o jogo tem uma entrada para o jogo inteiro. Uma ação de entrada dispara o `event.input` em todo objeto que tem o nó, e o movimento chega a todo personagem com entrada automática, inclusive o do bot. Para um jogo com vários personagens, a lógica escolhe quem reage, por exemplo por um atributo como `Jogador local`.
- **Sem rede:** não há salas, servidor nem partidas online. O estado de cada jogador pode ficar no próprio personagem, em atributos, e o da partida num objeto dela e nas variáveis do jogo, como no parkour de exemplo (o corredor guarda `Etapa`, `Tempo`, `Quedas` e `Checkpoint atual`; o `Controle da corrida`, a contagem), para o online da 0.8 reaproveitar a lógica.
- **Som:** o `oxy_simulate` e o `oxy_screenshot` não tocam nada; o relatório do `oxy_simulate` diz o que tocaria (`sounds` e `audio`). O agente não ouve o teste ao vivo; o Console diz quando o editor está sem dispositivo de som.
- **Pintura:** a pintura ainda não tem comandos próprios. `update_entity` edita os campos do objeto, mas não os pixels das texturas. As animações têm `set_clip` e `delete_clip`.
- **Importação:** só PNG e WAV, como no editor; um `.modelo.json` de outro projeto ainda não se importa (copie o arquivo para a pasta do projeto e confira o `oxy_validate`). Num projeto antigo, ao desfazer uma importação, a cópia continua na pasta `assets`.
- **Exportação:** só para Windows x64, como a engine. O executável tem o ícone genérico do Windows e não tem assinatura digital, e o `oxy_player.exe` precisa estar ao lado do editor (ao vivo) ou do `oxy-mcp.exe` (nos arquivos).

**Os testes**
- **Simulação:** o mesmo pedido repete os sorteios, que a semente (`seed`) decide, e os IDs das cópias do `action.spawn`. Os objetos e nós que o `setup` cria, ao contrário, recebem IDs novos a cada pedido (o relatório os lista em `setup`); por isso os sorteios dos nós `random.number` criados ou copiados no `setup`, as cópias feitas pelos nós e objetos que ele cria e o `state_hash` mudam de um pedido para outro. O teste que você faz no editor não é gravado: com a semente que o `oxy_status` mostra, cada nó `random.number` dá os mesmos números, na mesma ordem, mas as suas entradas e o tempo delas o agente precisa refazer em `inputs`.
- **Bot:** só no `oxy_simulate` e no `oxy_screenshot`, não no teste do editor, e um personagem por pedido. Ele segue os pontos em linha reta, sem girar a câmera, e não acha caminho sozinho: os pontos (onde pular, onde esperar) vêm do agente.
- **Teste ao vivo pelo agente:** o jogo corre em tempo real, no ritmo dos quadros do editor, então dois testes iguais não dão sempre o mesmo resultado: para conferir algo que precisa se repetir, use o `oxy_simulate`. O tempo do jogo só corre com a vista do jogo na tela (abrir a Lógica pausa o teste) e pode parar com a janela do editor minimizada; o agente vê isso em `advancing`. O clique por `point` é recusado, porque a vista do jogo no editor tem o tamanho do painel. O agente pode pausar o seu teste, mas não retomá-lo, pará-lo nem mandar entradas a ele.
- **Progresso salvo:** o agente não lê nem apaga o progresso do jogo exportado nem o do teste do editor, que também não aparece no `oxy_status` (as variáveis do teste aparecem, em `play.variables`). No `oxy_simulate`, o progresso entra pelo `save` e sai no relatório.
- **Pintura não salva nas capturas:** com o projeto aberto no editor, uma imagem pintada e ainda não salva aparece nas capturas do agente como está no arquivo salvo. Na vista do editor durante um teste, isso vale só para as imagens da interface do jogo; nas outras vistas do `oxy_screenshot` e no `screenshot` do `oxy_simulate`, vale também para as texturas dos objetos.

**As leituras**
- **Cópias de modelos:** no `place_model`, o `"$N@<ID>"` usa os IDs das peças, nós e animações como o modelo os guarda. O `oxy_project` com `model` lista as peças, com os IDs, mas as leituras não mostram os nós nem as animações de dentro de um modelo (o `oxy_entity` não chega lá). Esses IDs só se alcançam no lote que salva o modelo, encadeando os marcadores (`"$P@$S@<ID>"`, veja **Cópias no mesmo lote**). Para mudar a lógica de um modelo salvo num lote anterior, coloque-o, leia a peça colocada com o `oxy_entity`, mude-a e salve-a de novo no modelo com `save_model` e `replace`. As colocações já feitas não mudam com o modelo.
- **Console:** só ao vivo. Nos arquivos, sem editor aberto, o agente testa com o `oxy_simulate`, que traz os logs no relatório.

**Segurança**
- O canal só aceita conexões do próprio computador (`127.0.0.1`) e exige o token que o editor grava em `%LOCALAPPDATA%\OXY Engine\agents`. Desligar a opção fecha o canal e apaga esse arquivo.
- A importação lê só arquivos `.png` e `.wav` deste computador, pelo caminho completo, e escreve só na pasta do projeto (na pasta `assets` de um projeto antigo), fora das pastas que começam com ponto, dos atalhos e das subpastas que são outro projeto, sem nunca gravar por cima de um arquivo.
- O `oxy_scripts` lê e grava só arquivos `.luau` da pasta do projeto, fora das pastas que começam com ponto, dos atalhos e das subpastas que são outro projeto ou um jogo exportado (e as cópias que guarda em `.oxy/agente/`; renomear e excluir passam pelos comandos do `oxy_apply`, e excluir manda para `.oxy/lixeira`), e o `vscode` grava só `.oxy/`, `.luaurc` e `.vscode/settings.json` na pasta do projeto. Os scripts rodam numa caixa de areia: sem `os`, sem disco, sem rede e sem `require` fora da pasta do projeto.
- A criação de projeto escreve só o `project.oxy.json`, numa pasta nova ou vazia que você indicou, nunca na da OXY Engine nem na raiz de um disco.
- A exportação escreve uma pasta de jogo, com um executável, só onde você indicar: nunca na pasta do projeto, na da OXY Engine ou na raiz de um disco, e só substitui uma exportação anterior do mesmo jogo, quando você pede.
- Ao vivo, o agente só salva com **Permitir que agentes salvem** ligada, e só o projeto aberto, como o **Salvar** do editor, guardando antes o `.agente.bak`.
